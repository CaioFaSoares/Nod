## Decisions, findings and deviations

1. **`host.activate` refuses while a `host` row exists** —
   `Bond is already connected to a host — remove it first`. SP05 §2 keeps one guild at a time and
   `Repo.saveHost` replaces the row whole (B1 finding 5), so activating over an existing host would
   drop its bearer and snapshot silently. The switch path is "Remove host" (or `host.remove`) and
   then a join. Nothing in SP05 §3 says this either way; if the owner wants activation to replace in
   place, it is one `if` in `backend/main.ts`.
2. **At activation the Bond chooses the salt** (SP02 §1) and the host's answer to `/v1/auth/salt` is
   used for `iterations` only. `/v1/auth/salt` returns the *fake* salt for anyone not yet activated
   (H4's `saltFor`, `host/auth.ts:212-217`), which must never be stored as a person's real salt;
   SP02 §7's reset is "activation stores a **new** salt", which is what makes another machine's
   cached salt notice a reset. The salt is `randomSalt()` (16 bytes, base64url, 22 chars — the
   `SALT_PATTERN` of SP03 §2's body schema).
3. **Reset detection at sign-in is `row.salt !== saltResponse.salt`, and only for the same person**
   (`row.personId === token.personId`) — a different person signing in on this machine is not a
   reset and must not wipe anything. B3's connected `changePassword` updates `host.salt` through
   `repo.saveHostSalt`, so an ordinary password change does not read as a reset.
4. **Finding — `host.activate` does not wipe, and one path needs it.** The mandate wires SP02 §7's
   wipe at sign-in only, and that is what this slice implemented. But `host.remove` keeps the local
   `person` row (and its vault index), so re-joining the *same* guild on the same machine takes
   `host.activate` with a fresh salt (SP02 §1) for the same host person id: the old `vaultKey` is
   gone while the index rows are not. Today the keychain values are still plaintext (V1 is block 2),
   so nothing breaks yet; once `bv1.` lands, those items stop opening. The fix is three lines in
   `host.activate`: read `repo.personAuthByEmail(email)`, and when the stored verifier is a V2 record
   (`shared/auth.ts`, `PASSWORD_V2_ALGORITHM`) whose `salt` differs from the one the join cached,
   call `session.wipeVault(person.id)` before `adoptConnectedAccount`. Left out on purpose: the
   mandate fixes that flow step by step, and this is a scope decision about the person's data.
5. **Finding — SP02 §1 and H4 disagree about who picks the salt at activation.** SP02 §1 says the
   Bond chooses it (and §7 makes activation store a "new" one, which is the whole reset detector);
   `/v1/auth/salt`, on the other hand, answers a *fake* 16-byte salt for anyone not yet activated
   (`host/auth.ts`, `saltFor`). This slice follows SP02: `randomSalt()`, with the host's answer read
   for `iterations` only. If the owner wanted the host's salt reused, RF-43's reset detection (the
   cached-salt comparison on another machine) would stop working.
6. **`name` decides the route**: `host.activate` with `name` goes to `/v1/auth/setup` (SP02 §3,
   first admin), without it to `/v1/auth/activate`. The page derives the choice from the code's
   length (16 = setup, 8 = access, `CODE_LENGTH`/`normalizeCode` from `shared/host-api.ts`) and shows
   the Name field only then; no second click is asked of the person.
7. **The local name of an access-code activation starts as the email.** The host knows the person's
   name and no auth route returns it; the snapshot's `me.name` is the source (B4/B5's apply). The
   local row carries the email until the first sync. For the setup path the person types the name, so
   it is right from the start.
8. **`admin` at activation/sign-in is a best guess, on purpose**: `true` for the setup route (SP02 §3
   creates the first admin), otherwise `false`, and at sign-in the local row's current `admin`. The
   snapshot is the truth (B4/B5); a wrong `false` only hides the admin tabs until it lands, a wrong
   `true` would show tabs whose calls fail.
9. **`device.name` is `${os} ${arch}`** (`macos arm64`, …). The runtime has no device or host name
   (`backend/tiny.d.ts`: `TinyAppInfo` has `version`/`tinyjs`/`runtime`; `TinySystemInfo` has
   `os`/`arch`/`session`/`desktop`), and SP03 §2 fixes only the three fields. `appVersion` is
   `app.info().version`. A coarser name is used when `system.info()` refuses.
10. **The extra two auth calls ride a "pre-auth" connection**: `client.connect()` needs a `personId`
   for the keychain key (SP02 §5), which does not exist before the host answers, so the `salt`,
   `activate`, `setup` and `login` calls use a connection whose `personId` is `''` — the keychain has
   no item under that key, so `request` sends no `Authorization` header at all
   (`backend/host-client.ts`, `send` with `token === null`). The real connection (with the person id
   the host answered) is the one that stores the bearer and is the only one handed to `createSync`.
11. **Deep-link delivery is a push plus a pending value.** The runtime pushes `open-url` to the page
   itself (`~/.tinyjs/runtime/bridge.js:3407` and `:3653`), but only to a loaded page; the backend's
   own `onOpenUrl` therefore keeps the invite in `pendingJoin` and pushes it again on the next
   `session.state` call, which the page always makes at boot *after* it subscribed. `leitura` of
   `bridge.js` is what says the page load races the first push; the same pattern as RF-55's update
   notice (`UPDATE_FIRST_CHECK_MS`), without a timer.
12. **`host.remove` accepts and validates `keepPersonal` and does nothing with it** (SP05 §3's flag is
    block 2's decision about local personal tools; SP05 §2 keeps them in `tool` rows, and
    `Repo.clearHost` never touches them — B1 decision on `saveHost`/`clearHost`). The screen's label
    is "Keep my personal tools" with the honest hint that nothing in the keychain or catalog is
    deleted either way today.
13. **The signed-out state is a notice, not a redirect**: the sidebar/top notice says
    `${guild} signed this Bond out` and its "Sign in" button goes to Settings → Hosts, where the same
    join component is mounted in the password mode with the address, the fingerprint and the local
    email prefilled (it auto-discovers the pinned host, as `host.signIn` re-checks the key with
    `{ pinned }`, i.e. SP04 §1.4's `host key changed — remove and add the host again`).
14. **`host.discover` clears `pendingJoin`.** The invite is spent by the flow that began with it;
    without the clearing, every later `session.state` would re-open the join screen.
15. **No new dependency, no toolchain change, no new module.** Everything lands in the files of the
    slice's list; `src/api.ts` needed no change (finding 1 below is the one file outside it).
16. **`backend/sync.ts` is B4's** and landed while this slice was being written; `createSync`'s deps
    are wired exactly as its contract asked (`setInterval(run, ms)` → the runtime's, `clearInterval`
    takes the opaque handle back with one cast, whose reason is in the line above it). It was not
    edited.
17. **`shared/types.ts` carries the push `join`** — not in SP05 §3's table, which fixes only the RPC
    methods; the alternative was a second RPC method or a fourth blind push, and the type is the
    contract of that one event.
