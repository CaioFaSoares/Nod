## Acceptance criterion — how each item was met

| Issue #11 item | How it was met | Evidence |
| --- | --- | --- |
| `POST /v1/events` takes up to 500 events with client ids and returns the ids it holds. | The body schema is `t.Object({ events: t.Array(clientEvent, { maxItems: 500 }) })` with `id: t.String({ minLength: 1 })` — the client id is the idempotency key and cannot be empty; `MAX_EVENTS_PER_BATCH` is the single definition of the cap. The handler answers `{ acked: repo.addEvents(person.id, session.id, ctx.body.events, auth.now()) }`, which inserts the batch in one transaction and answers every id the host now holds, in batch order. Observed: 2 events → `200 {"acked":["s1","s2"]}`; 500 events → `200` with a 3401-byte `acked`; 501 → `400 {"error":"invalid body: events must not have more than 500 items"}` with no row written; the 501st is refused *before* any write, and the batch that is too large leaves the table untouched (asserted in the test). | `execucao` (curl, tests) |
| Sending the same batch twice leaves one row per event. | `repo.addEvents` is `INSERT … ON CONFLICT(id) DO NOTHING` (SP04 §5) and the route passes the batch through unchanged. | Events never carry query strings or fragments in `url`. | The route hands `url` to `repo.addEvents`, whose column rule is `shared/catalog.ts`'s `auditUrl` (`origin + pathname`, `null` when the address is refused), next to the `events.url` column — the route neither parses nor rewrites it, and the URL is never echoed in a response. ## Decisions and findings for the coordinator

1. **The kind list lives in the route, coupled to `shared/types.ts` by the compiler.**
   `EventType` is a type only — no runtime list exists in `shared/` (checked: `grep -rn 'EVENT_TYPES'
   shared/` finds nothing) — and `shared/host-api.ts` is not this slice's file, so the 24 kinds are
   spelled once in `host/routes/events.ts` as `KIND_SET: Readonly<Record<EventType, true>>`. Keying
   the object by the type refuses an extra kind (excess property) and a missing one (missing
   property), so the schema cannot drift from the type in either direction without a build failure.
   If the coordinator prefers one runtime list for host and Bond, it belongs in
   `shared/types.ts` (`export const EVENT_TYPES = […] as const satisfies readonly EventType[]`) and
   this object goes away — a two-line change this slice could not make.
2. **The body schema follows `ClientEvent` literally: `id`, `at` and `kind` are required, and
   `toolId`, `url`, `result` and `detail` are required but may be `null`.** `shared/host-api.ts` types
   them `X | null` (not optional), so a Bond that compiles against it always sends them. `id` is
   required non-empty because it is the primary key and the idempotency key; `at` is a non-empty
   string and the host does not parse it — the client clock is the source of the event's instant and
   the host stamps its own `received_at` (SP01 §2). **Finding:** if the owner wants the host to
   validate `at` as ISO 8601 UTC, that is one `pattern` on the schema plus a spec line, and the host
   still would not convert it.
3. **The 500 cap is inclusive and the refusal happens before any write.** 500 → `200`, 501 → `400`.
   The message is Elysia's, mapped by `host/app.ts` into SP03 §1's shape: `invalid body: events must
   not have more than 500 items` — the field is named and no request value travels.
4. **Finding — the ack is table-wide by construction.** `repo.addEvents` inserts under the *session's*
   person and then answers the ids the table now holds, without filtering by person (SP04 §5's
   "returns every id it now holds", literally). A batch that re-sends an id another person's row
   already holds is therefore acked, and the first writer's row stands untouched. Event ids are the
   Bond's own local event ids, so a collision is not reachable by accident, and no content of the
   sender's event is stored; my test pins the behaviour (row unchanged, id acked, `200`). If the owner
   wants the ack scoped to the caller, it is an `AND person_id = ?` in `repo.addEvents`
   (`host/repo.ts:1304-1309`) — H2's file, not this slice's.
5. **The caller is the session's, and the body has no person field.** `personAuth` + `callerOf` give
   the person and the session; the schema's object has no `personId`, and Elysia drops an unknown
   property from the parsed body (probed: `{"a":"x","zzz":1}` reaches the handler as `{"a":"x"}`), so
   a body that carries one is never read. Observed end to end: Bob's token plus `"personId":"p-ada"`
   stored `p-bob|p-bob`'s session.
6. **No rate limit on `/v1/events`.** SP02 §5's two budgets are the `/v1/auth/*` surface (H4 mounted
   them in a nested plugin for exactly that reason); SP04 §5 gives the push no budget, and the route
   adds none — an invented limit would refuse a legitimate backlog of 500-event batches.
7. **`host/context.md` needs three lines this slice may not write** (not in its file list): the status
   line ("H4 landed" → H5/H6/H8/the state of the block), the layout table (a row per group is already
   generic, but a status word for `routes/events.ts` and `events.test.ts` is where H4 put `auth.ts`
   and `auth.test.ts`), and the sentence "`snapshot.ts` and the remaining route groups (`routes/admin.ts`
   for H5, state for H6, events for H8) are still to come", which is now false. I report the exact
   change instead of making it.
8. **Pre-existing finding, outside this slice: `shared/auth.ts` does not typecheck under the repo's
   own settings.** `passwordCheck` (191,75) and `passwordCheckMatches` (206,73) pass a
   `Uint8Array<ArrayBufferLike>` to `crypto.subtle.digest`, which wants `BufferSource`; with
   `lib: ["ES2023","DOM"]` the TypeScript 5.9 `Uint8Array` default argument is `ArrayBufferLike` and
   the assignment fails. Reproduced on H4's landed files with the slice's own probe, so it is not from
   H8. `bun run typecheck`'s first step is `tsc -p tsconfig.json`, whose `include` is `["src",
   "shared"]`, so the gate will trip on it. One `new Uint8Array(localKey)` (or a typed-array generic)
   fixes both; the file is the `shared/` track's.
