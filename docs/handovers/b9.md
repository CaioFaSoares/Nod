## Acceptance — how each item was met

**1. `vault_item.origin` is stored on save and backfilled from `tool.origin`.**

- Stored on save: `Vault.save` computes the entry's canonical origin (`originOf(entry.url)`) and
  `saveVaultItem` writes it in the same statement as the rest of the item — also on the rewrite, so
  the origin always belongs to the credential as it is now. Read back through
  `Repo.vaultOrigin(personId, toolId)`. Proof: `test/vault.test.ts` — `origin › save records the
  entry origin…` (`execucao`), and `test/repo.test.ts` — `vault › saving the same pair…` plus
  `vault › the origin belongs to the credential…` (`execucao`).
- Backfilled: `migrate()` adds the column when the table exists without it and then
  `UPDATE vault_item SET origin = (SELECT t.origin FROM tool t WHERE t.id = vault_item.tool_id)
  WHERE origin IS NULL` — so an item saved by an earlier build takes the origin of its tool, and an
  item that already carries one keeps it. Proof: `test/repo.test.ts` — `schema versioning › a v2
  database from before the vault origin column…` (`execucao`): the fixture is a real v2 schema with
  the column dropped and one item inserted the old way (no `origin` in the `INSERT`), `user_version`
  at 2; after `migrate()` the item's origin is the tool's, the migrated `vault_item` is column for
  column the same as a fresh one, and a second `migrate()` neither throws nor loses it.
- Safe on an existing database, the v2 lesson included: the column is added by *presence* of the
  column, not by the version stamp, so a database whose table already exists is completed instead of
  silently skipped; `CREATE TABLE IF NOT EXISTS` still writes it for a fresh file, with the same
  shape the `ALTER` leaves (nullable, appended last).

**2. Changing a tool's URL (host or local) stops form fill for it; a test covers both cases.**

- The gate is in `cascadeContext` (`backend/tool-windows.ts:499`): `hasCredential` is true only when
  the vault item's stored origin equals the window's entry origin (`window.origin`, the canonical
  origin of the entry address at the time the window opened). With a mismatch the cascade behaves
  exactly like a tool with no credential — `inject` with `fill: false`, no attempt counted
  (`shared/login-cascade.ts` rules 4, 5, 7), the report path ending in `manual` — and the keychain is
  never read, so nothing secret enters the process for an origin the person did not save it for.
- Tests (`execucao`, `test/tool-windows.test.ts`), all with the real `backend/repo.ts` +
  `backend/vault.ts` behind the window dependencies and only the runtime faked:
  - `a credential saved for the entry origin is filled into the form (RF-38)` (`:841`) — `fill:true`,
    username and secret in the script, one keychain read.
  - `a local edit that moves the tool to another origin stops the fill (RF-38)` (`:859`) —
    `repo.saveEntry` with a new address (Settings), new window opens at it: `fill:false`, no
    `s3cret` in the script, `calls.credential === 0`, a `form` report reads `manual`.
  - `a host sync that rewrites the entry with another address stops the fill (RF-38)` (`:883`) — the
    entry arrives whole through `repo.saveEntry` the way a snapshot apply writes it (address and
    views): same result.
  - `an address change inside the saved origin still fills (RF-38)` (`:908`) — another path on the
    same origin keeps filling: it is the origin, not the page, that the credential belongs to.
- The data half of the same rule: `test/vault.test.ts › save records the entry origin; a moved tool
  does not move the saved credential` (`:255`) and `test/repo.test.ts › the origin belongs to the
  credential…` (`:541`) show that `saveEntry` with a new address leaves the stored origin alone, and
  that saving the credential again on the new address moves it with the entry.

## Decisions and deviations (for the coordinator)

1. **`VaultItem.origin` was not added.** `shared/types.ts` is not this slice's file; its owner (K1/Tan)
   confirmed at the start of the work that nobody is adding the field, and endorsed reading the
   origin through the repository instead. The row type therefore still has no `origin`; the value is
   read with `Repo.vaultOrigin(personId, toolId)`. If the coordinator wants the row type to carry it
   — for credential sharing in block 2, say — that is one field in `shared/types.ts` plus one line
   in `buildVaultItem`, for the shared owner.
2. **`Repo` gained `vaultOrigin` and `saveVaultItem` a required `origin`.** `docs/arquitetura.md` §4
   does not list either; `SP05 §2` mandates the column, and the fill needs a read of it. The
   parameter is required on purpose: a writer must state the origin, there is no silent `NULL` path.
3. **`ToolWindowsDeps.hasCredential` became `vaultOrigin`.** The origin check replaces the presence
   check — a credential only counts for the origin it was saved for — so keeping both would leave a
   dead dependency. `docs/arquitetura.md` §4 (`:211`, `:259`) still describes the old shapes
   (`saveVaultItem` without `origin`, `hasCredential`), and the cascade section itself is unchanged
   (`shared/login-cascade.ts` still asks `{ hasCredential, noFill }`; only where `hasCredential`
   comes from changed).
4. **`SCHEMA_VERSION` stays 2.** B1 owns `user_version = 3` and its own columns: the addition here is
   presence-guarded, not version-guarded, so B1's migration composes with it in either order. The
   `addColumns()` list (`:358`) is where B1's columns join.
5. **An item with a `NULL` origin fails closed**: `vaultOrigin` answers `null` and no fill happens.
   Only a database that never ran this migration can produce such a row, and the backfill fills it.
6. **The gate is synchronous** (in the cascade context), so a mismatched origin never reaches the
   keychain at all — the desync path that reads and then gives the attempt back is reserved for its
   original case (an index item whose keychain value is gone).

## What another owner must do

- **`backend/main.ts`** (integration slice, not this one): the window dependencies it builds
  (`backend/main.ts:124`) still pass `hasCredential: (toolId) => hasCredentialOf(toolId)`, and
  `hasCredentialOf` (`:229`) reads the index. It has to become the origin read:

  ```ts
  // in createToolWindows({ … })
  vaultOrigin: (toolId) => vaultOriginOf(toolId),

  /** The origin the credential of this tool was saved for; null without an item (RF-38). */
  function vaultOriginOf(toolId: Id): string | null {
    const r = repo;
    const person = currentPerson();
    return r === null || person === null ? null : r.vaultOrigin(person.id, toolId);
  }
  ```

  Until that lands, the deps object has no `vaultOrigin` at all: `signal`'s guard swallows the
  `TypeError`, so the cascade would stop silently — no fill for any tool (nothing secret leaks, but
  the feature is off). This is a hard dependency of this slice, not a suggestion.
- **`docs/arquitetura.md` §4**: the two stale lines named in deviation 3.
- Nobody else: `vault.save`, `vault.reveal`, `vault.list` and the page contract are unchanged, and no
  other file in the repository calls `saveVaultItem` or implements `ToolWindowsDeps`.
