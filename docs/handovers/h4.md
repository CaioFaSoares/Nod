(`docs/canonico.md` §14: RF-30…RF-55 approved by the owner on 2026-10-16; RF-32, RF-33 and RF-42 are

## Decisions and deviations for the coordinator

1. **The guards are plugins that read the app's decorations, and the scope is deliberate.** Elysia 2
   cannot type a decoration a plugin does not make itself, so `host/auth.ts` declares the shape once
   (`HostContext`) and confines the cast to `hostOf`/`callerOf`; everything above them is typed by the
   interface. I probed the beta's scopes before choosing: a hook or derive that arrives through a
   **nested** plugin reaches the mounting instance's later routes and stops there, while one
   registered directly on the mounted plugin leaks into the parent's later routes. That is why the
   address budget lives in its own nested plugin (`host-auth-address-limit`) inside
   `routes/auth.ts`, and why `auth.test.ts` ends with the regression guard "the budget and the guard
   of the auth plugin stay inside it" — H5, H6 and H8 mount their groups after `authRoutes`, and
   neither a 429 nor a 401 may reach them.
2. **`createApp` reads `host-secret` from `config.dataDir` instead of widening `AppDeps`.** `bootHost`
   already created the file; `main.ts` is not this slice's file, so the app loads it (H1 left it
   loaded and discarded). A second read of a 32-byte file at boot is the price.
3. **`AppDeps` is unchanged and `app.ts` builds the repo.** `createRepo(deps.db)` once per app, put on
   the context, never in a route module — the source test of `repo.test.ts` and H2's handover both
   asked for exactly that.
4. **413 is the answer to a body over the limit, and SP03 §1 does not name a status for it.** The
   table of §1 lists 400/401/403/404/409/429; the limit itself is in the same section. I used the
   HTTP status for "too large" rather than folding it into a 400. **Divergence to confirm**: if the
   owner wants it inside the table, the fix is one line in `app.ts`. The exception is read as "the
   routes whose body can carry an `entry.icon`": `/v1/admin/tools*` and `/v1/admin/bootstrap` get
   512 KB, everything else 256 KB. Without the bootstrap path a legitimate B8a body with icons would
   be refused.
5. **The address of a rate limit is the last hop of `X-Forwarded-For`, then the socket, then
   `unknown`.** SP02 §5 does not say where the address comes from; the container sits behind the
   proxy of SP07 §2, whose hop is the one entry an outside client cannot mint by prefixing the
   header. A request handed straight to the app (`app.handle`, or a peer that reaches the container
   without the proxy) shares the `unknown` bucket — the tests make that visible rather than hiding it.
6. **The email budget counts the failures of `login`, `activate` and `setup`** (every unauthenticated
   attempt that can guess a secret), **not** the password change, which is an authenticated path and
   whose failures must not lock a person out of signing in. The per-address budget counts every
   request to `/v1/auth/*`, exactly as "30 auth requests per minute" reads.
7. **The fake salt is the HMAC of the *normalized* email** (trim + lowercase, `shared/host-api.ts`'s
   `normalizeEmail`): SP02 §4 asks for a stable answer to repeated asks, and a person who retypes the
   address with a capital must get the same bytes.
8. **The dummy hash is memoized** (`hashAuthKey('bond/auth/dummy/v1')` on first use), so the first
   unknown-email sign-in pays one extra hash and every later one does not. The value is a hash of a
   constant, holds no secret and is never compared for its content.
9. **`POST /v1/auth/password` keeps the session and revokes nothing else.** SP02 §7 says that for a
   change ("keeps the session"); revoking the other sessions belongs to the reset by access code
   (`activate`), where the new salt already invalidates the old vault. The mandate's "revoke other
   sessions if SP02 says" resolves to "it does not say it here".
10. **`setup` creates the role `admin` (`id` and `name` `'admin'`, `admin = 1`) with `repo.saveRole`
    inside the transaction.** SP03 §2 gives the role's id and flag but not its display name; the id is
    the honest default for a guild's first role. A `setup` with a taken email is a **409** and rolls
    the code back with it — proved by redeeming the same code afterwards.
11. **One message for every token failure.** SP03 §1 allows "missing or invalid token" **and**
    `invalid credentials`; a missing, malformed, unknown, expired, revoked or disabled-person token all
    answer `401 {"error":"invalid credentials"}`, which is SP02 §5's single-message rule and tells an
    attacker nothing. `adminAuth` answers `403 {"error":"admin only"}` and nothing else.
12. **The argon2 hash and the token hash are computed before `repo.transaction`.** `bun:sqlite`'s
    transaction is synchronous, and the write must be one unit of work (H2 decision 14); the token is
    generated first, hashed before the transaction, and the row is inserted inside it. A rolled-back
    transaction discards a token nobody ever received.
13. **`repo.Device.os` is `string`, the wire `Device.os` is the three values of SP01 §2.** Passing the
    validated body into `repo.createSession` is the assignable direction (c1's finding only bites the
    read side, which is `GET /v1/sessions` — H5's).
14. **No new dependency, no toolchain change, no second boot path.** `Bun.password` and WebCrypto
    only; the CLI boots through `bootHost`, the same function `main.ts` uses.
15. **`host/context.md` gained the rules a later group must follow** — the guard pattern, the error
    mapping, the two rate limits, the body limit — because H5, H6 and H8 will each add one route file
    and one `.use(...)` line.
16. **`activate` does not refuse a person the host disabled; the guards do.** SP02 §3 couples a code
    to the person's email, not to their disabled flag, so a code bound to a disabled person can still
    be redeemed — and the token it returns is refused by `personAuth`/`adminAuth` on every request,
    because `authenticate` checks `disabledAt` (SP03 §1: "a valid session, person not disabled"). No
    privilege is gained, and a test pins the guard's refusal. If the owner prefers the refusal to
    happen at activation instead, it is one line in `routes/auth.ts` plus a spec line.
