## Acceptance criterion — how each item was met

### 1. "Tools, Roles, People and Activity tabs work against the host when connected, unchanged in local mode."

`leitura` of `backend/main.ts`: each of the ten handlers starts at the same place — parameters
validated exactly as before, then `const admin = hostAdminFor(connectionOf()); if (admin !== null)
{ …host route… }` and the original body below it untouched. `connectionOf()` builds a connection only
while a `host` row exists (RF-30), so local mode cannot reach the host by construction; the last test
proves the local writes of the same shape land in a real local repository while a reachable host
records zero requests.

`leitura` of the mapping in `backend/host-admin.ts`: every method names the SP03 §2 route it uses,
and the bodies are `shared/host-api.ts`'s types (`OrgTool`, `RoleRequest`, `PersonCreateRequest`,
`PersonUpdateRequest`, `GrantRequest`, `BootstrapRequest`), never a local row spread whole.

`execucao` (the test file, all against the real host):

- *a tool granted to a role reaches that role and nobody else* — `admin.saveTool` (the Tools tab's
  save) writes `jitsi` granted to `team`; the `team` member's verified snapshot carries it, the
  `finance` member's does not; `admin.grant('team','jitsi',false)` takes it away and `true` brings it
  back; `admin.saveRole`/`removeRole` move the guild's roles the same way; `admin.removeTool` empties
  the snapshot's org half.
- *editing a tool replaces its views and its grants on the host* — the same id saved again with other
  views, no grants, `active:false` and `auth.noFill`: the host answers exactly that.
- *the People tab* — `admin.listPeople` returns the guild's rows from `GET /v1/admin/people` (no
  `code`, `salt`, `authHash` or `token` substring in the answered bytes, and the code the create
  answered is not in the list), `admin.setRoles` returns the stored person, `admin.disable` fills
  `disabledAt` and kills the member's token at once (RF-39).
- *the Activity tab* — `admin.listEvents` returns the rows the host received with their own ids, the
  person/tool filters reach the host and the screen's `result` filter is applied on this side over the
  answered page.

The page half is `leitura`: `src/settings.ts` reaches all four tabs through the same RPC names it
always used (`catalog.list`, `catalog.get`, `catalog.save`, `catalog.remove`, `roles.list`,
`roles.save`, `roles.remove`, `roles.grant`, `people.list`, `people.setRoles`, `people.revoke`,
`events.list`, `events.syncStatus`), so no screen needed a new method; what changed is which card the
People tab draws and which entries the Tools/Roles tabs offer. **The pages were not run** (see "What
could not be done").

### 2. "'New access code' shows the code once with copy."

`leitura` of `src/settings.ts`: connected, the People tab draws the **New person** card and, per
person, a **New access code** button; both call `invites.issue` and render `inviteCodeBlock` — the
existing read-only input plus a **Copy** button (`navigator.clipboard.writeText`, the pattern this
file already used for a local invite) and "Save it now: this code will not be shown again." The code
lives in `state.invite`, is cleared when the tab changes (`selectTab`) and is never written to a file,
a row, an event or a log: `invites.issue`'s connected branch records an `invite_issued` event whose
detail is the roles and the expiry only, and the host returns a code exactly once (SP02 §3).

`execucao` of the backend half: the create answers one `XXXX-XXXX` code with a 72 h expiry, the list
that follows does not contain it, the code activates the person through the real `/v1/auth/activate`
route, a reissued code kills the previous one (401) and activates just the same.

### 3. "The owner adds Jitsi granted to `team`; after sync only `team` members see it (RF-34 acceptance)."

`execucao`, three layers of the same chain:

1. the admin write: `admin.saveTool` → `PUT /v1/admin/tools/jitsi` with `roles: ['team']`, answered
   with the stored org tool (host view id included);
2. the person: the `team` member's `GET /v1/state` — signature verified by
   `backend/host-client.ts` — carries `jitsi`; the `finance` member's carries nothing;
3. the sync: a real `backend/sync.ts` over a real repository, the host row and the member's bearer in
   the keychain, `syncNow()` → the verified body in `host.snapshot` holds `jitsi` for the `team`
   member. The two-instance smoke that observes it in the app is B11's (SP05 §5).

## Decisions and deviations for the coordinator

1. **An admin write goes to the host synchronously and is followed by an awaited `syncNow()`.**
   SP04 §4's outbox is the personal writes' path; an admin write that answered `200` and left the
   page's `catalog.list` unchanged would be the wrong screen. `afterHostWrite()` pipes `afterChange()`
   (this side's reload and the push) and then awaits `sync.syncNow()`, which re-arms the five-minute
   timer over the near-immediate one `afterChange()` armed — one run per write. A host that cannot be
   reached leaves the write where it landed and `host.state` says why; the admin method still answers
   what the host stored.
2. **`invites.issue` keeps its name and its `{code, expiresAt}` answer, and gains three optional
   parameters.** SP05 §3 says the method *becomes* "create person + access code, or reissue code for an
   existing person", and neither question can be asked with `{roles, days}` alone: connected it takes
   `email`+`name` (`POST /v1/admin/people`) or `personId` (`POST /v1/admin/people/:id/code`). `days`
   stays local-only — the host fixes 72 h (SP02 §3) — and is ignored while connected rather than
   refused, because the screen does not ask for it in that mode.
3. **Every user-facing message of a host failure is written on this side.** `backend/host-client.ts`
   deliberately reads no failing body, so `backend/host-admin.ts` maps the pair (failure, status) to
   its own sentence: `409` on `POST /v1/admin/people` → `email taken`; `404` on it → `the guild has no
   such role`; `404` elsewhere → `not found on the host`; anything else keeps the client's English
   message (`could not reach the host`, `signed out`, `the host refused the request`, …). No value from
   a request and no byte of the host's body travels — the test pins two of those messages.
4. **`people.revoke` connected is the host's disable, and it keeps the row.** `PATCH
   /v1/admin/people/:id { disabled: true }` ends every session of that person (SP03 §2, RF-39) and the
   People tab shows them as `revoked`. `deleteCredentials` is read (SP05 §3 requires the flag) and
   changes nothing: a guild member's credentials live on their own machine, and this machine's vault
   index has no row for them. The self-revoke guard is kept on this path too — the same screen must not
   be able to lock the admin out of their own account.
5. **`people.list` connected returns SP03 §2's `AdminPerson`, and `Person` gained two optional
   fields** (`activatedAt`, `disabledAt`). Without them the People tab would show a disabled person as
   an active one and offer a code that cannot sign them in. Local rows carry neither (the local table
   has no such column), which is why the fields are optional and the chips are conditional.
6. **The Activity tab reads the guild's log while connected, and `AuditEvent` grew by one union.**
   `GET /v1/admin/events` filters by person, tool and client-time range only (SP03 §2): the person and
   the tool go to the host, the screen's `result` filter is applied here over the answered page, and
   `sentAt` is the host's `receivedAt` — for a row read from the host, "is it on the host?" is exactly
   what the column asks. `AuditEvent.id` is `number | string` because a host row's id is a uuid; the
   page does not read the field, so nothing else moved.
7. **`catalog.get` now reads the effective catalog while connected** — B5 decision 8 named this read as
   the one the Tools tab would need, and without it "Edit" on a connected entry asks for a row the
   connected Bond no longer has. `probe` and `usualLogin` answer `null` while connected: the first is a
   local probe row, the second a local login history, and the host holds neither.
8. **Removing a connected entry does not touch the local row, its icon or the credentials saved for
   it.** The local catalog is not the catalog while connected (SP05 §2); deleting the local vault
   items of a tool that shares an id with the guild's would take the admin's own logins away on the
   guild's behalf. A6's cleanup stays exactly where it was, on the local path.
9. **A personal tool never travels on an admin route.** B5 hangs the person's personal views under the
   entry so the screens that open them can (SP04 §2); `orgTool()` and `catalog.get` strip them again,
   and both org tool writes refuse an entry the connected catalog calls `personal` (the grants of
   SP01 §2 are org-only, and the host's org tool row and a personal row are different rows). The Tools
   and Roles tabs list `guildEntries()` while connected for the same reason. In block 1 this is latent
   — nothing writes a personal tool yet — but the guard is what keeps block 2 from writing one into
   the guild's catalog by accident.
10. **The admin's own audit trail stays local.** A connected admin write records the same local event
    the local path recorded (`catalog_changed`, `roles_changed`, `grant_changed`, `invite_issued`,
    `access_revoked`) and SP04 §5 pushes it like any other; the Activity tab shows the guild's own log
    beside it. Nothing of the event carries a code, a password or a key — the create/reissue events
    name the roles and the expiry only.
11. **`catalog.exportToFile`/`importFromFile`, `events.exportToFile` and the whole Catalog tab stay
    local** (B5 decision 8; the issue's list names the four admin tabs, not the seed screen). While
    connected, an export writes the local catalog, which SP05 §2 keeps untouched on purpose.
12. **No new dependency, no runtime or toolchain change, no `src/style.css` edit.** `host-admin.ts`
    uses `fetch` through the existing client, `URLSearchParams` and nothing else.

## What could not be done

- **The Settings pages were not run.** No `tinyjs dev`, no `bun run app:dev` and no smoke: the runtime
  surface is B11's (the two-instance smoke, `test/smoke/`, being written in parallel) and running the
  app here would have taken the developer's port and the smoke's generated directory. Everything the
  page does is `leitura` of `src/settings.ts` plus the RPC the backend answers — which the test file
  executes over the real host.
- **No project gate.** `bun run typecheck`, the full `bun test test/` and the formatters are the
  coordinator's.
- **No measurement against a guild large enough to page the admin list.** SP03 §2 bounds `limit` from
  below only; `eventsQuery` passes the page's filter through and the host's own default is the bound.
