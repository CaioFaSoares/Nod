## Acceptance criterion — how each item was met

**1. "Sync runs on unlock, every 5 min on a backend timer, on 'Sync now' and after admin writes."**
`leitura` of `backend/sync.ts`: `start()` calls the run and the finished run arms
`SYNC_INTERVAL_MS` on the injected pair (the runtime's globals are `backend/main.ts`'s to pass, the
same pair that file already uses for the update check); `syncNow()` is the manual trigger;
`afterWrite()` arms `AFTER_WRITE_MS` (1 s) so a burst of writes coalesces. `execucao`:
*start() syncs once and arms the five-minute timer* (one snapshot request, one armed timer at
300 000 ms, the row carrying the verbatim body with its version and issuedAt), *the five-minute timer
runs the next sync*, *syncNow() with no loop running syncs once and arms nothing*, *a write asks for a
near-immediate sync, and a burst becomes one* (one armed timer at 1 000 ms, one extra sync after it
fires, the cadence back to five minutes). The loop is only armed by official triggers: it is B2's
`backend/main.ts` that calls `start()` on unlock, `stop()` on lock or remove, `syncNow()` for
`host.syncNow` and `afterWrite()` after admin writes — that wiring is on the real surface and is not
this slice's file.

**2. "Network off: state goes stale, cached tools stay, last sync time shown, offline badge in the
sidebar."** `execucao`: *a network failure is stale, keeps the cache and backs off to five minutes* —
`status === 'stale'`, `lastError` is the client's own message, `snapshot` is byte-for-byte the cached
body, `lastSyncAt` is untouched and the delays grow 30 s → 1 min → 2 min → 5 min and stay there;
*without a host row no sync reaches anywhere* (no request, `status: 'none'`). The state carries
`lastSyncAt`/`lastError`/`pendingWrites` for Settings → Hosts, and `orgToolsUsable` is the pure
function B5's catalog layer uses to stop showing the org half after 14 days of no success
(`execucao` of the boundary: 0 and 13 d 23 h usable, the completed day and 14 d + 1 s not). The
offline **badge** itself and the "last sync time" label are `src/app.ts` and `src/settings.ts` —
B2's UI, fed by `HostState`; this slice delivers the status and the counts.

**3. "401 clears the token and org data, keeps personal data, asks for sign-in (RF-39)."**
`execucao`: *forgets the token, drops the org half, keeps the personal half and asks for sign-in
once* — the keychain item is gone, `status: 'signed-out'`, `lastError` is the marker, the cached body
has `orgTools: []` and `roles: []` while `me`, the personal tool, the personal view and the favorites
are still there, the write that had not been sent is still queued, `onSignedOut()` ran exactly once
across two failing runs, and the identity fields (guild, address, issuedAt, version) stay for the
sign-in screen. *A network failure after a sign-out leaves the state signed out*, and *a successful
sync after the sign-in clears the state and brings the org half back*. The "ask" is the
`onSignedOut()` callback plus the `signed-out` status; the prompt on screen is B2's.

## What could not be done

- **No txiki.js run.** The loop is executed under Bun with an injected clock and interval pair. Its
  two runtime dependencies are the same ones `backend/main.ts` already uses under txiki.js — the
  global `setInterval`/`clearInterval` (the update check) and `crypto.subtle` through
  `fingerprintOf` (B1's measurement) — so this is `leitura` plus the shape of a proven call, not a
  measurement of its own.
- **SP04 §5's event push is not here.** It is B10 (#21): `event.client_id`/`sent_at` are still
  written by nobody and `EventType` has no `sync.rejected` (B1's and C1's findings). The run's order is
  therefore flush → `GET /v1/state`; the push belongs between the two, inside `runOnce`, and
  `createSync`'s deps are fixed by the cross-slice contract, so no seam was invented for a story that
  has not landed.
- **`sync.rejected` is not raised.** SP04 §4 pairs a refused (`4xx`) outbox row with that event; the
  row is dropped as the spec says, but the event cannot be written while `AuditEvent.kind` has no such
  value (B10's, per `docs/handovers/b1.md`). Nothing else about the verdict is missing.
- **No secret rule to prove by capture.** The module writes no log and no event, and the only strings
  it puts into `last_error` are `HostError.message` — which `backend/host-client.ts` builds from its
  own constants and never from a request or a host body (B1's tests) — or its own `SIGNED_OUT_ERROR`.
  The token, the password and the keys never enter this file: it holds a `HostConnection`, not a
  bearer.
- **Nothing on the real surface.** The sidebar badge, the Settings → Hosts screen and the sign-in
  prompt are B2's; the two-instance smoke (offline unlock, a queued personal tool, the reconnect) is
  B11's. What this slice proves is the state machine those surfaces read.

## Findings and decisions for the coordinator

1. **The sign-out state is persisted in `host.last_error`** (`SIGNED_OUT_ERROR` =
   "signed out — sign in again", exported). The `host` table of SP05 §2 has no sign-out column, and
   the fact has to survive a restart **and** guard the `ETag`: after a `401` the cached body is no
   longer the bytes the host signed, so offering its `version` as `If-None-Match` would earn a `304`
   that keeps the org half emptied *for good* after the person signs in again. The marker is sticky
   until a sync succeeds (`saveHostSnapshot` clears `last_error`), a failure of any other kind does
   not overwrite it, and while it is set the request goes out unconditionally. It is also, verbatim,
   what Settings → Hosts shows, which is the "ask for sign-in" of SP04 §3. If the coordinator
   prefers an explicit column over the marker, that is a change to SP05 §2's schema (H1/B2), not to
   this file's decisions.
2. **`clearOrgData` rewrites the cached body**, so the `snapshot` column stops holding the bytes the
   host signed. That is what decision 1's guard exists for: nothing reads the column as *bytes*
   (the client re-reads the host), and the rows it yields are the personal half plus the caller.
3. **`fingerprintOf` is imported from `backend/host-client.ts`.** `HostState.fingerprint` needs it
   and it is async, so it is computed once per pinned key and cached. B1's finding 1 (the function
   belongs in `shared/host-api.ts`, beside `CODE_ALPHABET`) still stands and would make this import
   a move.
4. **`shared/catalog.ts`'s `validateEntry` is deliberately not reused.** It drops `scope`, `ownerId`
   and the view `id`/`scope`/`ownerId` of SP04 §2 — exactly the fields a snapshot row must keep — so
   `shared/host-merge.ts` reads the spine itself. When `validateEntry` learns those fields (B2/B5),
   the two shape readers can meet in one place; until then the second one is the price of the first.
5. **`outboxVerdict` names `409` and the other `4xx` apart** (`drop` vs `rejected`), because SP04 §4
   gives them different consequences (the second raises an event). The ticket's "drop on 409/403" is
   satisfied — the row is dropped in both cases — and the pair exists only because the event does.
   `401` and `429` answer `retry`: neither judges the write, and dropping a person's offline write
   over an expired session or a rate limit would lose it for good.
6. **A failure after a sign-out keeps the signed-out state** instead of going stale. The session
   ended, nothing else can work until a sign-in, and overwriting the marker would re-arm decision 1's
   `304` trap.
7. **A changed host key stops the loop with status `stale`.** SP04 §1 gives no status for it: the
   cache is still what is shown, the message is the client's own exact string, and the person must
   remove and add the host — retrying cannot fix it, so no timer is armed. `syncNow()` still works by
   hand if a screen wants to prove the refusal again.
8. **`afterWrite()` is a no-op unless `start()` was called.** With no loop there is nothing to wake,
   and B2 starts the loop on unlock; a write made while locked cannot happen anyway.
9. **The 14-day window is half-open** `[lastSyncAt, lastSyncAt + 14 d)`: at exactly 14 days
   `orgToolsUsable` answers `false`, so the org half hides the moment the window completes. `null` or
   an unreadable date answers `false` too — failing closed is the only safe side when what is at
   stake is showing a guild's tools to someone the host may no longer admit.
10. **A `304` advances `last_sync_at`.** The host answered and the session is alive, so a healthy Bond
    whose state has not changed never falls out of that window — otherwise a person whose guild had
    no news for two weeks would lose their org tools while online.
