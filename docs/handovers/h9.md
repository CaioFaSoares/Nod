## Decisions and deviations for the coordinator

1. **The key copies carry the backup's timestamp stem.** SP07 §4 says the two key files are "copied
   beside each backup" and the database keeps the literal path `host-<ISO>.db`; one shared
   `signing-key.json` in `backups/` would be overwritten by every pass, so each backup carries its own
   pair as `<host-<ISO>>.signing-key.json` / `<host-<ISO>>.host-secret`, and `restore <file>` finds
   them from the file name. Every backup is then one findable triple and rotation removes three files,
   never one. §4's own sentence still holds; no line of §3–§4 was changed.
2. **A restore refuses a data dir that already holds anything.** SP07 §3 says "swaps it in" without
   saying what happens to a live directory; the issue's acceptance is a *fresh* volume, and refusing
   is the only version in which a restore cannot silently destroy live data. The message names the
   directory and the count, and the target dir is untouched. The consequence for the operator is that
   the backup must be outside the target data dir when restoring — it usually lives inside
   `/data/backups` — which §5.1 step 8 now spells out. If §3 is meant literally (restore over a live
   volume), the CLI needs an explicit argument saying "overwrite"; that is a contract decision for the
   coordinator, not one taken here.
3. **The backup settings are read in `backup.ts`, not in `config.ts`.** `host/config.ts` is not this
   slice's file. If the coordinator wants one environment module, `HostConfig` could gain
   `backupEveryHours`/`backupKeep`, `loadBackupSettings` would go away and `runBackup` would take the
   plain numbers.
4. **The two CLIs load the full environment**, so `restore` and `backup-now` require `BOND_PUBLIC_URL`
   exactly like the boot does (SP07 §2's variable is required and has no default). A lighter loader
   for the CLIs is a change in `host/config.ts`.
5. **The first scheduled pass is one interval after the boot** (SP07 §4's "every
   `BOND_BACKUP_EVERY_HOURS`"), so a fresh deploy has no backup until then; §5.1 step 7 tells the owner
   to run `bun run backup-now` once. A pass at boot would make every restart write a file.
6. **`VACUUM INTO` is synchronous** (`bun:sqlite`): a pass blocks the event loop for its duration. On
   a guild-size database that is milliseconds and the pass reads a consistent snapshot of a live
   database (observed with the host serving); moving it off the loop would need a second process.
7. **The connection stays in `migrations.ts`.** `host/repo.test.ts` requires that only `repo.ts` and
   `migrations.ts` name `bun:sqlite` and that only `migrations.ts` loads it; `backup.ts` therefore
   names neither the driver nor its constructor — it types the handle as `Host['db']`, runs
   `VACUUM INTO` on the handle the boot owns, and checks a restored database through `openDatabase`.
   Because that opener is the read-write WAL connection, the check runs on the **copy** in the target
   dir, never on the backup: a backup on a read-only mount stays readable, the backup file is never
   written to, and a rejection deletes the copy, leaving the target as empty as it was found. The
   check's own side files (an empty `host.db-wal`, the `host.db-shm` index) are removed, so the
   restored dir is exactly the triple. This was reported by H4 as two defects in my files (a failing
   rule test and a `tsc` error) and both are fixed; the verification is in "Commands run" 4. H4 also
   updated `host/context.md` while this slice was open, so its rows already read `backup.ts`:
   "`VACUUM INTO`, rotation, restore" and `cli/*.ts`: `setup-code`, `backup-now`, `restore`; the only
   wording left is in "For other owners".
8. **`bun run <script>` only works from `/app/host` inside the container**: the image copies
   `shared/` and `host/`, so `/app/package.json` does not exist. §5.1's steps name the `cd`, and the
   compose proof used `-w /app/host`. A Dockerfile whose `WORKDIR` is `/app/host` with
   `CMD ["bun", "main.ts"]` would remove that wrinkle; the Dockerfile is H1's file.

What was **not** changed: the public contract (no route, no shape, no persistence format), `config.ts`,
`keys.ts`, `migrations.ts` and its migration 1, the compose service/volumes/ports, and every doc other
than SP07 §1 and §5.

## What could not be done

- **Item 3 of #12 (`bloqueada`): the deploy on the owner's Coolify, and `/health` through the public
  address.** It needs the owner's Coolify project and the address the proxy will expose; the owner
  decided the address is set at deploy (`docs/canonico.md` §14 "Host address"), so nothing here can
  name it or reach it. What is reachable was done and is in "Commands run" 3: build from the repo, one
  service with a healthcheck, `/health` 200 on the published port, a container recreation that keeps
  the `kid`, the person and the backups. `docs/specs/SP07-host-deployment.md` §5.1 carries the steps
  the owner (or the coordinator) runs when the gate opens.
- **The Bond-side half of item 2** ("the same people sign in, and a pinned Bond accepts the host" as
  seen by the app) is not observable in this slice: signing in needs `host/auth.ts` and the `/v1/*`
  routes (H4, H5/H6) and a Bond that pins the host (SP05). What is proven here is the layer underneath
  it — a restored data dir boots with the identical `kid` (so a pinned Bond keeps accepting the host,
  SP04 §1) and with the identical person, salt and `$argon2id$` hash (so those credentials are the
  ones the restored host will verify).
- **A second replica or a WAL-checkpointed backup** is outside SP07 §2 (one replica) and RF-41.
- The off-VPS copy stays deferred by the owner's decision; nothing here writes outside the volume.
