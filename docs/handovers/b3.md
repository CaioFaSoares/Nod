## Acceptance criterion — how each item was met

**1. Connected accounts use `PasswordHashV2` with the host salt; unlock works offline.**
`execucao` of `test/session.test.ts`: `adoptConnectedAccount` writes the row of
`host-person-1` with `password_algorithm = 'BOND-KDF-V1'`, an empty `password_hash`, the **host** salt
(`AAECAwQFBgcICQoLDA0ODw`, the base64url of 16 bytes) and `check = base64url(SHA-256(localKey))` of
the keys the host has, and the session's `keys()` are those same bytes. After `lock()`, the same
password unlocks with `hostRecord()` still `null`: the salt is on the person row, and the session has
no `fetch` and no host client among its `deps` at all (`leitura` of `SessionDeps`), so no network can
be involved. The backoff (RF-23) covers that path too: five failures arm the 1 s wait and the right
password is refused inside it.

**2. A v1 local account migrates to V2 on its first unlock.**
`execucao`: a row created by `repo.createPerson` with `hashPassword` unlocks once; the row comes out
`BOND-KDF-V1` with a **fresh** 22-character base64url salt (≠ the v1 salt), `iterations` of the
session, `check` of the keys of that salt, and `password_hash = ''`; the second unlock goes through
V2 and a wrong password is refused. The old hash stops deciding: a test puts a valid PBKDF2 hash of
the right password back by hand and spoils the `check` — the right password no longer opens the row.
A failed unlock leaves the v1 row exactly as it was. `leitura` of `backend/session.ts:357-364`: the
migration is keyed on the row's algorithm (`!== BOND-KDF-V1`), which is SP02 §6's "local mode only" —
a connected account is created with V2 at activation (`SP05 §2`), so no connected account can reach
that branch.

**3. Password change updates the host and the local verifier; the vault keeps working (RF-24).**
`execucao` of the connected change: the host receives exactly one
`{ currentAuthKey, newSalt, newAuthKey }` where `currentAuthKey` is `base64url(authKey)` of the
current password under the row's salt, `newSalt` is a fresh 22-character base64url salt and
`newAuthKey` is the same for the new password — all three 43/22 characters of base64url, the two keys
different, and the serialized request contains neither password (RF-42). After it, the row verifies
the new password over the new salt, the old password fails, `keys()` hold the new keys, and the
keychain item plus the index row are the same ones (`vault.read` still answers the credential). When
the host refuses (a throwing `host`), the request was made first and the local verifier is unchanged:
the old password still unlocks and the new one does not. Without a host callback the local row is
rewritten as V2 with a fresh salt (the local path). A wrong current password or a short new password
reaches the host zero times.

**4. A salt change at sign-in (reset) triggers the vault wipe flow of SP02 §7.**
This slice owns the wipe, not the detection. `execucao` of `wipeVault(ana)`: the index rows and the
keychain items of that person are gone (`bond.cred.<ana>.kanban` deleted), the other person's item
and row are untouched and still readable, no session is needed (the wipe runs before anyone can
unlock) and nobody is locked out. `leitura` of `backend/main.ts:937`: B2 detects the change at
sign-in — `if (same && row.salt !== published.salt) await s.wipeVault(row.personId);` — before
`adoptConnectedAccount` at `backend/main.ts:946`. **B2 dependency, and it is wired**: the detection,
the "your saved logins will be removed" notice and the E02 key regeneration (SP06 §2) are B2's, and
the issue's remaining half belongs to the host round trip of B11's smoke.

## What could not be done

- **No project gate, no typecheck of the whole project.** Command 2 covers the three files this slice
  touched (and, as a reading, `main.ts`'s use of them), not the repository.
- **No run against a real host.** The activation and sign-in round trip (SP03 §2's
  `/v1/auth/activate`, `/v1/auth/login`, `/v1/auth/salt`) is B2's wiring and B11's two-instance smoke;
  here the host is a double that records what it was called with. The bytes it would receive are the
  ones pinned above.
- **No re-encryption of the vault with the new `vaultKey`.** SP02 §7 and §8 give that to story V1
  (`bv1.` encryption). Today's items are the plaintext `{username, secret}` JSON of `backend/vault.ts`,
  which is why RF-24 holds here by *not touching* them; the crash-between-the-two-steps rule of §7 is
  V1's too.
- **No `send`/event for the wipe.** There is no event type for it in `shared/types.ts` (B2 owns the
  file), and `backend/vault.ts` records no event at all; B2 decides what the audit carries around the
  reset flow.

## Findings and decisions for the coordinator

1. **`main.ts`'s `confirmLocalPassword` and a V2 account — found and already fixed by B2.**
   It verified with `repo.personByEmail(...).password` and `verifyPassword`; after this slice that read
   is the v1 projection, so for a connected account (and for any account after a change or a
   migration) `hash` is empty and the check would fail forever — `vault.exportToFile` would answer
   `incorrect password`. It was reported to B2 (`agent://B2HostsScreen`) and B2 applied the two-line
   fix: `leitura` of `backend/main.ts:704-711` now reads `r.personAuthByEmail(person.email)` and
   `verifyStoredPassword(password, record.password)`. No action left here; recorded so the next reader
   of the projection knows why `personByEmail` stays: it is the only non-additive change of this slice,
   and `leitura` of the repository shows its only other consumer is that one call
   (`grep -rn personByEmail test/ src/ host/ backend/`, plus the host's own `host/repo.ts`, another
   module). Every other change is additive, so `test/vault.test.ts`, `test/seed.test.ts`,
   `test/sync.test.ts` and `test/tool-windows.test.ts` — none of which is a file this slice may run —
   keep reading the same rows.
2. **A connected change keeps the cached host salt in step — decided here, confirm it.** SP05 §2's
   `host.salt` is "the host salt, for offline unlock", and SP02 §7's change moves the host's salt.
   B2's sign-in calls a salt other than the cached one a reset and wipes the vault
   (`backend/main.ts:937`), so a stale cache would wipe the vault of someone who only changed their
   password — RF-24 broken by the combination of two correct slices. `changePassword` therefore calls
   the new `Repo.saveHostSalt(newSalt)` when it has a host callback: the salt column and nothing else
   (the snapshot, the version and the pin stay — `saveHost` would have dropped the cached org
   catalog). `execucao` in `test/session.test.ts` (the host row's salt follows, the snapshot survives)
   and `test/repo.test.ts`. If the coordinator prefers the detection to read the **person** row's
   salt instead, `saveHostSalt` becomes redundant — but the cache would then be wrong for every other
   reader of `HostRecord.salt`.
3. **A v1 row unlocked while a host is configured still migrates.** SP02 §6 says the migration is
   "local mode only", read here as "only a v1 row migrates, and a connected account is never v1"
   (`leitura` of the branch). The alternative reading — skip the migration whenever a host row exists —
   was not taken: it would leave a leftover local account on v1 with no `vaultKey`, and it adds a
   branch SP02 does not ask for. The coordinator decides if the other reading was intended.
4. **`createAccount` still writes a v1 row** (`hashPassword`, unchanged). The issue's item 2 is the
   migration, and SP02 §6 only fixes V2 for a connected account; a new local account therefore reaches
   V2 on its first unlock (and gets its `vaultKey` there). `keys()` is `null` right after
   `createAccount`, until that unlock. Story V1 (vault encryption) should say whether new local
   accounts are to be created as V2 directly.
5. **`wipeVault` cannot delete a `bond.cred.*` item the index does not know.** `SecretStore` has
   `get`/`set`/`delete` and no enumeration, so the wipe goes through `removeVaultOf`, which is the
   index. An orphan item (a row deleted by hand) is unreachable by design; if the owner wants it
   swept, the keychain interface has to grow an enumeration first.
6. **The biometric item survives a reset.** SP02 §7 lists the `bond.cred.*` items, the index and the
   E02 keys — not `bond.bio.<person>`. With today's marker (a person id) that is harmless; once V1
   puts `base64url(vaultKey)` in it (SP02 §9), a reset would leave the **old** `vaultKey` in the
   keychain after the vault was wiped. Nothing was changed here (biometrics stay as they are, as the
   mandate says); the flow that clears or rewrites that item belongs to V1 with the reset path.
7. **`docs/arquitetura.md` §4 is now behind.** Its `session.ts` block still lists
   `changePassword(current, next)` and none of the new methods, and it is not a file this slice may
   edit. The signatures are in `backend/session.ts`'s `Session` interface.
