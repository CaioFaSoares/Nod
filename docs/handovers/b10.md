## Acceptance criterion — how each item was met

**1. "Unsent events go up in batches of ≤ 500 and are marked sent from the host's ack."**
`execucao` of `bun test test/sync.test.ts`: *1200 unsent events go up in three batches of 500/500/200,
oldest first, all marked sent* — the three `POST /v1/events` bodies carry 500, 500 and 200 events, the
concatenated ids are exactly `unsentEvents(1200)`'s order, `eventSyncCounts()` is `{ sent: 1200,
pending: 0 }`, and the fourth call of the run is the `GET /v1/state` (no empty batch is assembled).
The first event of the first batch is `{ id: <uuid>, at, kind, toolId, url, result, detail }` exactly —
`ClientEvent`'s seven fields, no more. *A partial ack marks only the acked ids* — a batch of three the
host confirms one id of leaves `{ sent: 1, pending: 2 }`, and only that id carries a `sentAt`; the two
unacked ones go up again in the same run, and the push stops there instead of asking for the same rows
forever. `execucao` of `bun test test/repo.test.ts` covers the repository half: `addEvent` stamps a
fresh uuid (`/^[0-9a-f]{8}-…-[0-9a-f]{12}$/`, different per row, `sentAt: null`), `unsentEvents` answers
oldest first and at most `limit`, `markEventsSent([id, 'not-an-id'])` marks exactly one row and a
second ack of the same id keeps the **first** receipt (`12:00` survives a `13:00` ack). `leitura`:
`backend/sync.ts`'s `pushEvents` is called between `flushOutbox` and `fetchSnapshot` inside `runOnce`,
which is SP04 §3's order and the seam `docs/handovers/b4.md` named.

**2. "Settings → Activity shows sent vs pending."**
`execucao`: `eventSyncCounts()` is what the new `events.syncStatus` answers (`bun test
test/repo.test.ts`: sent/pending counts through every marking step, `{ sent: 0, pending: 0 }` with no
events). `leitura` of `src/settings.ts`: `load()`'s `activity` case reads `events.syncStatus` **only
when a host is known** (`state.eventSync = hasHost() ? await call('events.syncStatus') : null`),
`viewActivity()` draws `Sent <n> · pending <m>` above the table when it is non-null, and appends a
`Sent` column whose cell is the event's `sentAt` or `pending` (`event.sentAt ?? 'pending'`). **The
counter line and the column are hidden when the Bond knows no host** — canonico §13's "enquanto não
houver host, o evento é local e privado" — and visible for `connected`, `stale` and `signed-out`
alike, because those three differ only in whether the host is reachable, not in whether the rows are
going up (a stale Bond shows them all `pending`). "Knows no host" is a **status**, not a missing
object: `host.state` — and `host.remove`'s answer — is a `HostState` whose status is `none` for a Bond
that has none (SP05 §3), so the check is `hasHost()` (`status !== 'none'`) and not `host !== null`;
that rule has a name because it is not obvious from the type. The tab is read again when a `host` push arrives
(`on('host')` → `void load()`), so a run that moved rows from pending to sent is visible without
leaving the screen. **Limitation:** the Activity screen itself was not executed — this repository has
no DOM test and the mandate forbids the smoke; the view is `leitura` and its wiring is B11's
two-instance smoke.

**3. "Resending a batch creates no duplicates on the host."**
The host's half is H8's and already proven (`host/events.test.ts`: the same batch twice → one row per
event, `received_at` of the first kept; `execucao`). This slice's half, `execucao` of `bun test
test/sync.test.ts`: *a failure keeps every event pending with its client id, and the next run sends
the same ids* — the first run's `POST /v1/events` fails (`could not reach the host`), the state goes
`stale` and the snapshot is **not** fetched (the run stopped at the push), `eventSyncCounts()` stays
`{ sent: 0, pending: 2 }`, and the second run's batch carries the **same two ids** in the same order;
the pair is then marked and counted `{ sent: 2, pending: 0 }`. Both runs come from one row each: the
client id is written with the row (`backend/repo.ts`), never regenerated, so the host's
`ON CONFLICT(id) DO NOTHING` sees the same key. The repository side pins the same property from the
other end: the lazy backfill answers the *same* id on every call, so a row that predates the column
cannot duplicate itself either.

The rest of the story's mandate, each `execucao` of the two files: **no push without a host** — two
events, `clearHost()`, one sync → `status: 'none'`, no request at all, `{ sent: 0, pending: 2 }`;
**SP04 §4's `sync.rejected`** — a `403` on an outbox write drops the row and writes exactly one event
`('sync.rejected', '403', 'PUT /v1/personal/tools/mine', <host person id>)`, which the same run then
pushes (`kind` on the wire), while a `409` drops the row and raises nothing.

## Decisions and findings for the coordinator

1. **The client id is a uuid, not the local rowid.** SP04 §5's "(the local event id)" is satisfied by
   the event's own local identity, and `SP01 §2:114` is explicit that the host's `events.id` is a
   *client-generated uuid* and the idempotency key. A rowid would have been wrong for a second reason:
   the host's ack is table-wide (`h8.md`, finding 4), so two machines of the same person — each
   numbering its rows from `1` — would collide and the second machine's events would be dropped as
   duplicates by `ON CONFLICT(id) DO NOTHING`. The uuid is generated in `addEvent`, so the id exists
   from the moment the row does.
2. **The backfill is lazy, and nothing in the schema moves.** B1 already wrote both columns and their
   `addColumns` entries (`backend/repo.ts` in `1d839b0`), so `SCHEMA_VERSION` stays `3` and `migrate()`
   is untouched. `unsentEvents` fills `client_id` on the rows that are unsent and still null, right
   before it reads them: a Bond that never connects writes nothing extra, and the write is bounded by
   the rows that actually need pushing. A row that is already `sent_at` can never be one of them (the
   ack matches by client id), so a second backfill pass is a no-op.
3. **`AuditEvent.clientId`/`sentAt` are optional, and the push narrows them.** `PendingEvent` (repo) is
   the type `unsentEvents` answers with — `AuditEvent & { clientId: string }` — so the wire mapping
   cannot put an empty id in a batch, and `listEvents` (which does not backfill) can still describe a
   legacy row honestly. Optionality is also what keeps every existing `addEvent` call site (`main.ts`,
   `seed.ts`, `session.ts`, `tool-windows.ts`) compiling unchanged: the input type excludes both fields,
   so the repo stays the only writer of a row's identity.
4. **The push loop stops when a batch confirms nothing.** Termination is the reason: a host that acks
   a subset always shrinks the pending set by at least one row (the marked ones leave it), and a host
   that acks none ends the round instead of re-asking forever. The alternative — one batch per run —
   was rejected because SP04 §5 says "up to 500 unsent events" without tying the rest to a later run,
   and a backlog of 1200 would otherwise take 15 minutes to drain at the healthy cadence.
5. **Finding — the pre-host backlog is pushed.** SP04 §5 says "the **existing** local events gain
   `sent_at`" and pushes "up to 500 unsent events, oldest first", with no cutoff, so every event a
   local-mode Bond recorded before a host was added goes up with the first sync. canonico §13's
   "enquanto não houver host, o evento é local e privado" can be read as a promise that those events
   stay local; §13's next clause ("Com o host, ele é enviado em lote") is what this slice implemented.
   If the owner wants the stricter reading, the change is one `WHERE at >= ?` in `unsentEvents` against
   `host.added_at` plus a line in SP04 §5 — a scope decision, not this slice's to make.
6. **Finding — a refused batch fails the whole run.** SP04 §5 has no verdict for a `4xx` on
   `/v1/events` (an older host that does not know a kind answers `400` and writes nothing), so the
   `HostError` raises out of `pushEvents` and SP04 §3's machinery reacts: the state goes `stale`, the
   backoff starts, and the events stay pending with their ids. Nothing is lost or duplicated, but a
   version skew can hold the snapshot back until the host is upgraded. The cross-side kind union makes
   a skew a same-commit change on the host side; if the owner wants a Bond that survives the skew, the
   decision is what a refused batch does (drop it? split it? retry with the offending kind removed?) —
   and it changes the spec, not only the code.
7. **The `sync.rejected` event carries the route and the status, nothing else.** `personId` is the host
   person id (`connection.host.personId` — the local person of a connected Bond *is* the host person,
   SP05 §2), `result` is the status code, `detail` is `METHOD path`. The write's body and the host's
   answer never touch a row (canonico §13's no-secret rule); the path is a route with a slug in it
   (`/v1/personal/tools/mine`), never a value.
8. **The counters are their own RPC, not a richer `events.list`.** `events.list` is filtered and
   capped (default 500, `EventFilter.limit`), so counting what it returns would count the page the
   Activity screen happens to be showing, not the table. `events.syncStatus` answers the two counts
   with one query each. `events.list` *also* carries the per-row half through `sentAt`, which is
   additive to `AuditEvent` — the JSONL export gained the same two fields, because it serializes the
   same row (canonico §13's format is a line per event, not a closed field list).
9. **The Activity lines are gated on a host, not on `status === 'connected'`.** Reason in acceptance
   item 2. What stays out of scope: the "New access code" half of that screen and the People/Tools/Roles
   tabs are B6's, and `src/context.md`'s table row for this screen already names B10.
10. **One existing test's script changed, and why.** `test/sync.test.ts`'s *a 409 and a 403 drop the
    write: neither can be replayed* refused **every** call, including the events push this slice added.
    A `403` now raises `sync.rejected`, which the same run pushes, so "the rest of the run still
    happened" would have been asserted against a host that refuses everything — no longer a host of
    SP03 §2. The script now refuses the outbox write and acks the events route; the test's own
    assertions (`listOutbox`, `pendingWrites`, the snapshot) are untouched, and the two verdicts'
    different consequences are pinned by the new `sync.rejected`/`409` tests of the push block.

11. **The pushed `url` is the column's, and the column is already trimmed.** SP04 §5's "no secret, URL
    as `origin + pathname` only" has one writer per event kind and all of them apply
    `shared/catalog.ts`'s `auditUrl` before `addEvent` (`backend/tool-windows.ts`'s four recording
    call sites — `tool_opened`/`view_opened`/`login`/`load_failed` — and `backend/main.ts:1588` for
    `external_opened`; every other event carries `null`), which is what the comment beside the
    `events.url` column states. `pushEvents` therefore hands the row's value over unchanged, and H8's
    route applies `auditUrl` again as its own guard. A second strip inside the sync loop would be the
    same fact in two houses; what B10 pins is that the wire body carries the row's value verbatim
    (`execucao`: the first event of the first batch is `{ …, url: 'https://alpha.example.test/app' }`).
