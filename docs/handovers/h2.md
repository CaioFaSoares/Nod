## Decisions and deviations for the coordinator

1. **The `Repo` interface is the contract, and its errors carry the status.** `createRepo(db)`
   returns `Repo`, whose methods throw `ConflictError` (409), `ForbiddenError` (403) or
   `NotFoundError` (404) — the statuses of SP03 §1 — so H5 maps an error without interpreting it.
   Every message is static English: SP03 §1 forbids an echo of the request, so no message names an
   id, an email or a code.
2. **`personAuthByEmail` is the only read that returns `salt` and `auth_hash`.** `personById`,
   `personByEmail` and `listPeople` never select them, so `GET /v1/admin/people` (SP03 §2, "no salt
   or hash") cannot leak them by accident. `CodeRecord` and `SessionRecord` never carry
   `code_hash`/`token_hash` either.
3. **Time is an explicit parameter.** Every writing method takes the caller's ISO 8601 UTC string
   (`now`), and personal writes take the Bond's `updatedAt` (SP04 §4). That is what let the tests
   move the clock to prove the 72 h / 24 h TTL and the 5-wrong-tries death without waiting, and it
   keeps `new Date()` out of the data layer.
4. **The TTLs live in the repo**, as the single definition wired to the purpose:
   `CODE_TTL_MS = { activate: 72 h, setup: 24 h }` (SP02 §3), `MAX_CODE_ATTEMPTS = 5` (SP02 §3),
   `SESSION_TTL_MS = 14 d` (SP01 §2, SP02 §5). H4 passes the code hash and gets the stamps.
5. **An expired code is dead by its own stamp**: `redeemCode` answers `null` and writes nothing —
   it does not spend an attempt and does not revoke the row. The fifth *wrong* try is what revokes
   (`attempts = 5`, `revoked_at = now`). A caller replaying an expired code therefore sees "invalid
   code", which is the single auth failure of SP02 §5.
6. **The last-admin guard is a before/after count inside one transaction**: activated, non-disabled
   people holding an admin role. A change that would leave none throws and the whole transaction
   rolls back (role set, disable, role delete, demoting the `admin` role) — proved by the tests
   asserting the state is untouched after the refusal. The guard is silent while no admin exists,
   which is what lets an empty host be built and the first admin activated (SP01 §2's "once the
   first admin is activated"). An admin *created but not activated* is not counted: the repo refuses
   removing the last activated one even if an unactivated admin exists (test
   "a second activated admin makes the first one removable").
7. **SP01 §2's definition of "can see" is a grant to one of the person's roles, or their own
   personal entry.** `entries.active` (a disabled org tool) is *not* part of it, because SP01 §2
   does not list it; a favorite of a deactivated org tool therefore survives. If the owner wants
   deactivation to drop favorites too, it is one predicate in `repo.ts`.
8. **Favorites are pruned by a global predicate, per person.** After a role change, a grant revoke
   or a role delete, the repo deletes every favorite whose entry is no longer visible *to that
   favorite's person* — so one person's loss never touches another's list (tested with two people
   sharing a role and with a second role keeping the grant).
9. **Favorites are replaced wholesale, with a per-person stale guard**: a `PUT` older than the
   newest stored `updated_at` of that person's list answers 409, which is what the outbox replay
   expects (SP04 §4: `409` → drop the row and take the host's version). A staleness check needs no
   extra column: `max(updated_at)` of the list is the list's version.
10. **Org tool writes carry the host clock; personal writes carry the Bond's `updatedAt`.** SP03 §2
    gives the admin body as `OrgTool` (Entry + views) with no timestamp, while a personal tool
    carries one, so `saveOrgTool(tool, now)` stamps `updated_at` and `savePersonalTool` keeps the
    client's value (last-write-wins, SP04 §4).
11. **`views.ord`**: an org tool's views are written in the order the write carries them (`ord` =
    index), because the Bond's `View` has no order field; a personal view is a single row and is
    stored at `ord = 0`. A personal view hanging under an org entry belongs to *that person*, so a
    tool's own view list never shows it (the snapshot's `personalViews` carries it instead).
12. **`events.url` is sanitized in the repo** with `shared/catalog.ts`'s `auditUrl` before storing:
    the column is annotated `origin + pathname only (auditUrl)` in SP01 §2 and a query string may
    carry a token (SP04 §5). A URL the helper refuses is stored as `null`.
13. **`addEvents` follows SP04 §5 literally**: `INSERT … ON CONFLICT(id) DO NOTHING`, then answers
    the ids the host now holds, deduplicated, in batch order. The 500-event cap of SP03 §2 is the
    route's body schema, not the repo's.
14. **`transaction()` is part of the contract on purpose.** `POST /v1/auth/setup` must redeem the
    code, create the person, create/assign the admin role and open the session as one unit; without
    the exposed unit of work H4 would leave a spent code behind on a failure. Nested calls become
    savepoints (`bun:sqlite`), which is also how the last-admin guard wraps its write. The test
    "a composed write is one unit of work" shows both the rollback and the committed composition.
15. **A finding from the tests, worth knowing for every later slice**: SQLite counts the rows an
    `ON DELETE CASCADE` takes with the deleted row in `changes`, so `changes === 1` is wrong for
    `roles` and `entries` (roles alone gave 2, an org tool 4). The presence checks read "< 1 means it
    was not there".
16. **`setMeta` refuses `schema_version`** (409): that key belongs to `applyMigrations`, and a route
    writing it would make the next boot throw. `meta.guild_name` and `meta.created_at` are exposed
    through `meta`/`setMeta` but nobody writes them yet — SP04 §1's `Discovery` and the boot owner
    need to decide who does (see "for other owners").
17. **No row type was added to `shared/`.** The host rows are declared in `repo.ts` and keep the
    field names of `Entry`/`View`/`Person` (`order`, `roles`, `views`, `auth`, `active`, `scope`,
    `ownerId`, `updatedAt`), while `Person`, `Role`, `AuthOverride` and `View.mode` are imported from
    `shared/types.ts` — a snapshot can hand a `HostTool` over where an `Entry` is expected, without a
    rename and without the host depending on the `Entry.scope/ownerId` change that
    `shared/context.md` lists under H2 (see "for other owners").
18. **No new dependency, no toolchain change.** `host/` still depends on Elysia alone; the repo uses
    only `bun:sqlite` through the handed-in connection. No project gate was run (typecheck, the full
    `bun test test/`, the smoke, formatters): the mandate allows `bun test host/` and the
    measurements above, which is what ran.

## For other owners

- **H4 (`host/auth.ts`)**: use `issueCode` / `redeemCode` / `personAuthByEmail` / `activatePerson` /
  `changeAuth` / `createSession` / `touchSession` / `personById`; `CODE_TTL_MS`, `MAX_CODE_ATTEMPTS`
  and `SESSION_TTL_MS` are the only definition of SP02 §3's and SP01 §2's numbers. Compose
  `POST /v1/auth/setup` inside `repo.transaction(…)` (see decision 14). `redeemCode` answers `null`
  for every failure — unknown, expired, revoked, used, out of tries — which is what keeps the single
  `invalid code` message honest.
- **H4 / `cli/setup-code`**: the guard "refuses when an admin exists" maps to `repo.adminCount()`
  (activated, non-disabled admins — the count SP01 §2 protects). If the command must refuse while any
  *person with an admin role exists at all, even unactivated*, that is a different query: a decision,
  not a repo gap.
- **H5 (routes)**: build the repo once — `createRepo(deps.db)` in `createApp`, or a single call per
  request — and never import `bun:sqlite` in a route module (the acceptance of #5 and the source
  test in `host/repo.test.ts` both depend on that). Map `error.status` for `RepoError`. The personal
  tool id pattern `^p-[a-z0-9]{10}$` (SP03 §2) belongs to the body schema (a 400 from SP03 §1), not
  to the repo. The auth level "admin" is `person.admin` from `personById`. `PUT /v1/admin/tools/:id`
  passes the host clock as `updatedAt`; the personal routes pass the Bond's.
  `GET /v1/admin/people` uses `listPeople()`.
- **H6 (`host/snapshot.ts`)**: `listRoles`, `listPersonalTools`, `listPersonalViews`, `favorites`,
  and `orgToolsFor(personId)` for a person or `listOrgTools()` for an admin; `meta('guild_name')` for
  `Discovery`. `HostTool`/`HostView` carry the `Entry`/`View` field names plus the host columns.
- **Boot (`host/main.ts`)**: `meta.created_at` (and `meta.guild_name`, from the deployment env of
  SP07 §2) have a home in `repo.meta`/`repo.setMeta` and no writer yet.
- **Coordinator / `shared/`**: `shared/context.md` lists `Entry.scope/ownerId` (and the `View` ids)
  under H2, but this slice's file list does not include `shared/types.ts`, so it was left untouched —
  `shared/host-api.ts` is being written in parallel by another owner and the host repo does not
  depend on either change. The coordinator decides who lands `shared/types.ts`.
- **Specs**: no divergence was found — migration 1 copies SP01 §2 verbatim, and the values, the
  statuses and the messages follow SP02 §2–§5, SP03 §1–§2 and SP04 §4–§5. One observation for the
  spec, not a fix: `access_codes.code_hash` is `UNIQUE` (SP01 §2), so a code string can never be
  issued twice in the life of a database — harmless for random codes, relevant to any test or import
  that reuses one.
