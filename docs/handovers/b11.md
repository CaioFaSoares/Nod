### Why a runner and not a `bun test` file

`run.ts`'s recipe is the only way this repository repeatedly observes the real surface, and it
cannot be imported (it ends in `process.exit(await main())`), so this slice repeats the parts it
needs — `temporarySeed`, `gen-config`, the launch, `killTree`, `waitForResult` — and keeps its own
rules (`dataDir` per app id, the nonce, the desk). The duplication is small, is inside `test/`, and
the alternative (exporting from `run.ts`) would have edited a file SP05 §5.1 freezes.

## Decisions and findings for the coordinator

1. **The codes never touch a file.** The setup code comes from `host/cli/setup-code.ts` into the
   runner's memory and P's access code from the admin's page into the same memory: both travel
   through a loopback endpoint the runner serves ("the desk", `GET /desk/admin`, `POST /desk/handover`,
   `GET /desk/person`, `POST /desk/host`), and the page fetches them with `tiny.fetch` at the moment
   it needs them. Nothing is written to the generated page, to `store.json`, to a log or to an error
   (the desk answers static messages and logs no request). The alternative — the code in the
   generated page or in the app store — would have put a secret in a file, which `AGENTS.md` forbids.
   The desk is also the smoke's "network" switch, because SP05 §5.5's network-off is the host process
   and only the runner can stop it.
2. **The two contract names are read at run time, not guessed.** `test/smoke/connected.ts` parses
   `ApiContract` out of `shared/types.ts` and takes the publish method from
   `host.bootstrap`/`catalog.bootstrap`/`admin.bootstrap`/`host.publishTools` (first present) and the
   person-create method from `people.create`/`invites.issue`; it also reads whether the publish
   method declares `void` (run with no arguments) or a `tools`/`roles` body, and whether the
   person-create method names an `email`. The header prints what it resolved
   (`publish=host.bootstrap body=false, person=invites.issue email=true`), so a future rename is one
   line of output away instead of a silent failure. This is how the smoke could be written and run
   before B6 (#18) and B8a (#19) landed — and the run in command 2 is what "the handler is not there
   yet" looks like.
3. **`events.syncStatus` is admin-only, so P cannot see its own counters.** `backend/main.ts`
   (`ADMIN_ONLY`, line 471 at this read) gates `events.syncStatus` beside `events.list`, so a member's
   machine cannot read sent/pending. The smoke therefore observes B10's "what was sent" on the
   admin's machine (`4.3b`: sent 7, pending 0) and proves **P's** rows — including the two written
   while the host was down — by reading the host's own SQLite (`backend/main.ts` is not this slice's
   file; `docs/handovers/b10.md` left this gate as an open decision for H5). If the owner wants a
   person to see their own sent/pending line, the change is one line in `ADMIN_ONLY`; the screen
   half is the Activity tab, which is an admin tab (B6/B10's), and this smoke already has the step
   for it (`5.9`, removed here).
4. **B5's finding 3 still stands, and this smoke does not hide it.** `vault.save` needs a local `tool`
   row (the foreign key of `vault_item.tool_id`), and a *host-only* tool has none. Step `3.7` passes
   here only because both app ids apply the smoke's temporary seed, so `tool-a` exists locally on P's
   machine with the same id the host published — exactly the case `docs/handovers/b5.md` describes
   ("in the block-1 smoke both sides exist"). A tool that only ever existed on the host still cannot
   receive a credential; the decision is the coordinator's, not this file's.
5. **Sequential launches, two dev ports.** Both instances are the same app, and `tinyjs.json` holds
   one dev port, so two simultaneous `tinyjs dev` would fight over it. The runner launches one at a
   time (still "two machines" for the smoke's purposes: different app id, different data dir,
   different dev port, both against the same host), and the state that has to survive a restart — the
   `host` row, the cached snapshot, the local verifier — is in the app data dir, which is what the
   later phases read.
6. **The nonce, not the app id, decides a result is fresh.** The same app id boots twice (admin in
   phases 1 and 3, person in phases 2 and 4), and `store.json` keeps the previous result; the runner
   puts a fresh uuid in the page of each launch and ignores any `smoke_result` whose nonce differs.
   Without it the second launch of an app id would read the first one's answer and pass for free.
7. **`locked` is the proof that the backlog went up.** `5.4` locks the session while the host process
   is gone, so a `locked` row can only exist on the host because the reconnect pushed it. The runner
   fails the run when P's rows are absent or when `locked` is not among them, so a host that acked
   only the events recorded while online cannot pass.
8. **The old `test/context.md` paragraph was wrong, not just stale.** It said the two-instance smoke
   "starts the host from `host/compose.yaml` on loopback". Nothing in block 1 did that: the smoke
   boots `host/main.ts` on a temp data dir and needs no Docker (SP05 §5 says "on two machines, or two
   app ids on one machine", and SP04 §1 allows plain `http://` in dev). The section now describes
   what runs.
9. **`bond://join` is not exercised, on purpose.** `docs/handovers/b2.md` (what another owner must
   do, 7) recorded that `urlScheme` is a packaged-`.app` feature, so the deep link cannot be observed
   under `tinyjs dev`; SP05 §5's steps do not ask for it either — they add the host through the same
   `host.activate` the join screen calls.
10. **The smoke holds its own ports.** The host's `PORT` refuses 0, so the runner reserves a free port
    through a temporary `Bun.serve` and releases it for the host; the app's dev ports are 5199 and
    5200, never a developer's 5173. Nothing but `127.0.0.1` is ever addressed.

## What could not be done

- **Step 1 of SP05 §5 is not run by this slice.** It is the existing local smoke
  (`bun test/smoke/run.ts`), and the mandate forbids this slice to run it. What this slice states is
  `leitura`: `run.ts`, `smoke.html` and `tools.ts` are untouched (command 3), so the local smoke
  executes the same code it did before.
- **No two-machine run.** "Two machines" here is two app ids on one machine (SP05 §5's own
  alternative): one OS, one keychain, one loopback. The credential never leaves the machine in either
  case (the vault does not sync, §17 of `docs/canonico.md`), so what a second machine would add is a
  different keychain — not this slice's question.
- **No container, no TLS, no DNS.** The host runs as a process on loopback; `BOND_DEV=1` is what
  allows the plain `http://` address (SP04 §1). `host/compose.yaml` and the Coolify deploy are H9's
  and SP07's.
- **No DOM test.** The Settings screens the codes are shown on (`src/settings.ts`, B6's) are not
  exercised: the page drives the RPC the screens call. A button that fails to appear is a screen bug
  this smoke cannot see.
- **No secret capture.** Nothing here proves RF-42 by wire capture (that is B2's item 3 and the
  owner's own capture); what the smoke proves is that no code, token or password reached its output
  or its files.
- **No new dependency, no toolchain change, no alias, no re-export**: `package.json`, both
  tsconfigs, the lockfiles and `tinyjs.base.json` are untouched, and the smoke needs only what the
  local one needs (`tinyjs` on `PATH`, Bun, the runtime's keychain).
