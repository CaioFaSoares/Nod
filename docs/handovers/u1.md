Note for the coordinator, not a blocker: the workflow triggers on a branch named `release-*` and now
tags `release-<version>`, so a branch named exactly `release-0.2.0` shares its name with the tag.
Branches and tags live in separate git namespaces, so the release is created at the branch's commit
(`--target github.sha`) and a later push to that branch does not move the tag; the tag is what
`releases/latest/download/manifest.json` follows.

## How to observe it (for the coordinator)

The notice needs a release channel: a seed whose `update.url` points at a manifest with a higher
`version` (`docs/distribuicao.md` §1, §6, §8). The owner's current `resources/seed.json` has
`update: null` (`tinyjs.json` in the repo has no `update` block — `leitura`), so nothing appears and
nothing is checked today; that is the acceptance item "no notice when not available", observed as an
empty notice slot.

1. Packaged app with the channel set: open it and unlock. Within ~5 s the bar above the content reads
   `Version <latest> available`, with `Install` (admin), `Details` and `×`. No Settings visit.
2. `Details` → Settings → Account, the Version card, with its own `Check for updates`.
3. `Install` → Activity shows `update` / `requested`, then the app swaps and restarts (A13). Only an
   admin gets the button; `bond.installUpdate` refuses the rest.
4. `×` → the notice disappears; `store.json` (the runtime `store`, `paths.data`) holds
   `"dismissed_update": "<latest>"` and nothing else; quit and reopen → still hidden; the Version
   card still reports the available version.
5. Publish a higher `version` (tag `release-<version>`) → the notice returns, because the dismissed
   string no longer matches.
6. Channel that cannot be reached: no notice, and one `update` / `failed` row in Activity.

Known dev-only artifact, declared and not worked around: `app.update.check()` also answers in
`tinyjs dev` when the seed names a channel (the version comes from `tinyjs.base.json`), so a dev
process with such a seed shows the notice while `install` refuses with "auto-update only works from
the packaged .app build" — the runtime exposes no public "is packaged" answer to gate it
(`docs/tinyjs.md` §10-§11).

Declared limitation of the delivery: the backend pushes; the page does not pull. The first check
waits 5 s (the same wait the runtime's own background check uses) so a page that is loading still
catches the push, and `afterUnlock` re-pushes whatever the backend already knows, which covers a
session that was locked when the check ended. A page that took longer than 5 s to load *and* stayed
unlocked would only see the notice at the next check (24 h). Making that delivery pull-based would
need the notice in `AppInfo` (or another method), a contract change this slice does not ask for.

## What could not be done

- No execution of the notice itself. Proving it needs a packaged build with a manifest served on a
  channel; neither exists in this repository (the seed is private and outside git, §1/§7). The
  observation recipe above is the hand-off for that run.
- `.github/workflows/release.yml` only gets its tag from a real push; the check above reproduces the
  computation, it does not run the workflow.
- The runtime also checks on its own when `tinyjs.json` has `"update": { "auto": "daily" }`, which
  `scripts/gen-config.ts` writes from the seed. It never installs by itself — it pushes the page
  event `update-available` and fires `onUpdateAvailable` — so it is harmless, but it duplicates the
  manifest GET our watch makes. `scripts/gen-config.ts` is not mine: whoever owns it decides whether
  to drop `auto` or keep both checks.
