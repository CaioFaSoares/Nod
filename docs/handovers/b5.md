## Acceptance criterion — how each item was met

### 1. "Connected mode reads org tools/roles/grants from the verified snapshot; local tables stay untouched."

`leitura` of `backend/connected-catalog.ts`: there is no `tool`/`role` read anywhere in it — the only
input is the `host` row the caller read, and `build()` takes the org half from `rows.orgTools`, the
roles from `rows.roles` (verbatim, `SP04 §2`'s "all roles of the guild") and the grants from each
entry's own `roles`. `leitura` of `backend/main.ts`: `visibleEntriesOf()` returns `connectedEntries`
when `connectedMode` and only touches `repo.listEntries()` otherwise; `catalog.list` goes through
`listedEntries()`; `roles.list` is `rolesOf()`; every one of them picks the connected answer from the
in-memory catalog, never by writing to a table. The `tool`/`role`/`tool_grant`/`tool_view` rows are
never written by this slice at all.

`execucao`:
- *the org tools and the roles are the snapshot ones, and the local tables stay untouched* — a Bond
  whose host row was synced with the snapshot's `jitsi` and roles `team`/`finance`, while the local
  database holds `local-kanban` and `local-role`: the effective entries are `['jitsi']`, the effective
  roles `['team','finance']`, the four local catalog tables are **byte for byte** what they were
  (every row of `tool`, `tool_view`, `tool_grant`, `role` compared as text before and after), the
  local entry is still in `repo.listEntries()` and `local-role` is not among the effective roles.
- *an entry keeps what the host sent* — the effective entry's `roles` (the grants), `views`, `icon`,
  `order` and `scope` are the host's values, untouched.

### 2. "A grant added on the host shows the tool after the next sync, only for people with that role."

`execucao`:
- *a person with the granted role sees the tool; another role does not* — the same `jitsi` granted to
  `team`: the person whose snapshot says `roles: ['team']` sees `['jitsi']`, the one whose snapshot
  says `roles: ['finance']` sees `[]` (the local visibility rule of `shared/catalog.ts` is reused:
  `active` plus a grant to one of my roles, or `me.admin` for the whole guild).
- *a grant added on the host shows the tool after the next sync, only for that role* — v1 with no
  grant → `[]`; the next sync brings v2 with `jitsi` granted to `team` → `refresh` answers `true`,
  the entries become `['jitsi']` and `current().version` is `'v2'`; the same v2 for the `finance`
  person stays `[]`.
- *a sync that changed nothing reopens the window without re-reading the body* — the push signal is
  "what the page would see changed", so a `304` that only moves `last_sync_at` answers `false` while a
  sync that brings the org half back (the reopened window) answers `true`.

On the real surface the same chain is `backend/sync.ts`'s `onState` → `refreshConnectedCatalog()` →
`afterCatalogChange()` → `push('catalog')` + `push('tools')`, which the page already handles
(`on('catalog')` → `catalog.list`, `on('tools')` → the sidebar). `leitura` of `backend/main.ts`; the
two-instance smoke that observes it end to end is B11 (`SP05 §5`).

### 3. "A tampered snapshot is rejected and the previous cache stays."

`execucao`, both halves:
- *a tampered body is refused by the client, and the previous cache stays* — a real loopback server
  signs the body of SP04 §2 with a generated Ed25519 key and `backend/host-client.ts` verifies it
  (path B1 built); a correctly signed body becomes a row and the catalog shows `['jitsi']`; the server
  then serves the same body with **one byte changed** while signing the original bytes, the client
  refuses it with the `signature` failure, `host.snapshot` still holds the first body byte for byte,
  and the catalog keeps answering `['jitsi']`.
- *a stored body that is not the document keeps the previous cache* — a row whose bytes are `not
  json`, a JSON body of another `api`, and a body whose `me.id` is another person: all three are
  refused (`refresh` answers `false`), the entries stay `['jitsi']`, and `current().version` stays
  `'v1'` with the entry's own fields — the catalog answers with the body it is showing, not with the
  row it refused.

### Extra, from the same spec sections (not in the checklist, both are observable)

- **SP05 §4's sidebar order** — `execucao`: with favorites `['beta','mine']` over org `alpha`/`beta`
  and personal `mine`, the entries are `['beta','mine','alpha']`; an unresolvable or repeated favorite
  is skipped; a personal view hangs under its entry after the entry's own views (the index
  `tools.openView` uses), and a view of an entry the person does not see travels nowhere.
- **RF-37's 14-day window** — `execucao`: at `lastSyncAt + 14 d − 1 ms` the org half is shown, at
  exactly `+14 d` (`docs/canonico.md` §22, half-open) it is hidden and the personal half stays, and a
  favorite of a hidden org tool goes with it. The guild's roles stay (see decision 6).

## Decisions and findings (for the coordinator)

1. **The cache key is the body bytes, not the `version`.** SP05 §2 says "parsed once per change" and
   the ticket says "keyed by snapshot version"; the `401` path (`shared/host-merge.ts`'s
   `clearOrgData`, B4's decision 2) rewrites the cached body **under the same version**, and a version
   key would keep the pre-sign-out org half forever. The bytes are strictly stronger: a version that
   moves always moves the bytes with it.
2. **The effective catalog carries the parsed body's `version`, not the row's.** A signed body that
   passes the client but not `parseSnapshot` still lands in the row (the sync does not parse); the
   catalog then keeps showing the previous body and must not claim the new version.
3. **`me.id` has to be the row's `personId`.** The host signs per person, and the local `person` row
   of a connected account *is* the host person id (SP05 §2), so a body naming somebody else is refused
   like an unreadable one — fail closed, because what is at stake is a guild's catalog.
4. **Visibility is one rule, reused.** The org half goes through `shared/catalog.ts`'s `visibleEntries`
   (`active` plus a grant to one of my roles, or `me.admin` for the whole guild — SP04 §2: the host
   already filtered, and this is the same defense in depth the local mode has); the personal half only
   through `active`, because SP04 §2 says those are mine by construction and their `roles` is empty.
5. **A `host` row with no readable snapshot shows nothing.** SP05 §2 reads the org half from
   `host.snapshot`; there is no fallback to the local tables, so a Bond that joined while offline
   shows an empty catalog until the first sync succeeds. The alternative (showing the local catalog)
   would present tools the guild may not grant. RF-40's "no local tool disappears" is the personal
   side of the join (B7, block 2), not a fallback here.
6. **Past the 14-day window the org *tools* hide and the guild's roles stay.** The owner's decision is
   about tools ("keeps showing org tools from the cache for 14 days … then hides them until a sync
   succeeds", `docs/canonico.md` §22) and `Entry.roles` is where the grants ride, so the org half goes
   whole. The role names are not what the window protects — SP04 §2 says they are not secret inside
   the guild — and the screens that read `roles.list` while connected are the admin ones, which are
   already degraded offline. If the coordinator reads the decision as covering roles too, it is one
   line in `build()`.
7. **The vault records the origin of the entry the person is looking at.** `createVault` receives a
   repository whose `entry()` answers the effective catalog (`{ ...database, entry: catalogEntryOf }`
   in `main.ts`) — the same object, one method answered differently while connected — so `Vault.save`
   computes the entry's origin from the **host** entry's url (SP02 §8, RF-38). Without it, an admin
   who moved a tool's url on the host would leave every re-saved credential pointing at the old origin
   and the cascade would never fill that tool again.
8. **`catalog.get`, `catalog.exportToFile` and the admin writes still read/write the local tables.**
   The ticket puts the admin write routing in B6, and neither read is on its list; the pages that call
   them are the admin tabs, whose host routing is SP05 §4's (B6). Recorded so nobody reads the gap as
   an oversight.
9. **`people.list` stays local.** SP04 §2's `people` is a block 2 member of the snapshot; nothing in
   block 1 reads people remotely.
10. **`refresh`'s answer is "what the page would see changed".** It is what decides the push, so a
    healthy Bond whose state did not move (a `304`, or a sync that re-reads the same body) tells the
    page nothing: the sidebar and Home do not reload every five minutes.
11. **The window is evaluated at the read that follows the verdict.** The catalog rebuilds when the
    body or the `orgToolsUsable` verdict moves, so a Bond that sat idle past the 14 days hides the org
    half the moment an entry is read; while unlocked the sync publishes a state every five minutes
    (and on every failure), which re-derives it and pushes the change to the page.

## What could not be done

- **No txiki.js run.** Everything ran under Bun: the module has no runtime dependency at all (the row
  is a parameter, the clock a dependency), and the only runtime-shaped call in the new `main.ts` code
  is `Date.now()`, which the sync loop already passes. The app itself, its windows and the two-instance
  smoke are B11's.
- **No secret rule to prove by capture.** Nothing in this slice writes a log, an event or a row: the
  module holds the snapshot's rows in memory and the entries it hands out are the entries of that
  body. The bearer, the password and the keys never enter the file (`backend/host-client.ts` reads the
  keychain; `backend/sync.ts` owns the row writes).
- **Not on the real surface.** The screens (`src/app.ts`, `src/settings.ts`) are B2's and the pages
  were not run; what this slice proves is the answer every read of the catalog layer now gets, and
  the push that tells the page.

## What another owner must do

1. **B10 (#21) — one line in this slice's file, if the gate is wanted.** `events.syncStatus` is wired
   in `backend/main.ts` as
   `'events.syncStatus': () => required(repo, 'events.syncStatus').eventSyncCounts(),`, placed with
   the other event methods and **not** in `ADMIN_ONLY` (the counters are this machine's own rows and
   `src/settings.ts` reads them only under a host). If the counters should be admin-only like
   `events.list`, it is one line in `ADMIN_ONLY`. Nothing else of B10's slice needed anything here:
   `SyncDeps`/`Sync` are unchanged and `onState` keeps its shape.
2. **B6 (#18) — the admin routes.** `catalog.get`, `catalog.exportToFile`, `catalog.save`,
   `catalog.remove`, `roles.save`, `roles.remove`, `roles.grant`, `people.*` and `invites.issue` still
   read/write the local tables; when they move to the host routes, `afterChange()`'s
   `sync.afterWrite()` (already wired) is what makes the next sync publish the new state, and
   `catalog.get`/`catalog.exportToFile` are the two reads of the catalog that would then want the
   effective catalog (they are one call away from `catalogEntryOf`).
3. **Coordinator / the vault's owner — a host-only tool cannot receive a credential (blocked path,
   not fixed here).** `backend/vault.ts` reads `repo.entry(toolId)` for the origin and
   `vault_item.tool_id` has a foreign key to `tool(id)` (`backend/sqlite.ts` opens the database with
   `PRAGMA foreign_keys = ON`). A tool that exists only on the host has neither, so `vault.save` fails
   with `unknown tool`, or — if the entry existed and the row did not — with a raw
   `FOREIGN KEY constraint failed`. In the block-1 smoke both sides exist (the admin publishes its own
   tools, so the host entry reuses the local id), and the origin is then the host entry's url as
   decision 7 says. The fix is a decision, not a patch: either the effective entries get a local
   `tool` row while connected (which SP05 §2's "untouched while connected" forbids), or
   `backend/vault.ts`/`backend/repo.ts` take the credential's entry from the effective catalog and
   `vault_item` stops requiring a `tool` row. Outside this slice's files either way.
4. **Coordinator — `src/app.ts` needs nothing from this slice** (`leitura` in "Files touched"): if a
   reviewer wants the connected sidebar to mark org vs personal entries, that is a screen decision
   SP05 §4 does not ask for in block 1.
5. **Coordinator — `docs/arquitetura.md` §4** does not name `backend/connected-catalog.ts` (§3 already
   lists `shared/host-merge.ts` for B5, and §4's `main.ts` line says "admin methods routed to the
   host when connected" — B6's).
