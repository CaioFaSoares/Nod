## Decisions and deviations for the coordinator

1. **`personAuth` is mounted before `adminAuth` inside the admin group — a defect found in the
   documented guard rule, exactly on this slice's shape.** `adminAuth` alone in a plugin group makes
   every admin route answer `500`. Measured in isolation with two deriveless look-alike plugins:
   `new Elysia().use(adminAuth).get(…)` → the trace is `admin` only, and its derive reads `person` as
   `undefined` (the nested `personAuth` never runs); `new Elysia().use(personAuth).use(adminAuth).get(…)`
   → `person > admin > route`, each hook exactly once. H4's own test only ever mounted `personAuth`
   on the parent instance before `adminAuth` (their handover: "a derive that arrives through a nested
   plugin reaches the mounting instance's later routes and stops there"), which is why the flat case
   passes and the group case does not. Told H6 in our cross-slice exchange; the corrected rule is in
   `host/context.md`, my file. **For `host/auth.ts` (H4's file), one line of documentation to decide**:
   the comment on `adminAuth` could name the requirement, or `adminAuth` could be re-shaped — but the
   workaround is already correct and costs nothing per request (Elysia applies each named plugin once,
   measured), so I did not ask for a change in a file I do not own.
2. **All 14 admin routes live in `routes/admin.ts`, `/v1/admin/events` included.** H8's
   `routes/events.ts` (already landed) carries `POST /v1/events` only; I checked and it names no admin
   path, so the two groups do not collide. If the coordinator wanted the admin event list with the
   event group instead, one route moves and one test moves with it.
3. **The entry-id slug is enforced; the other ids are not.** The path `:id` and the body `id` of the
   tool routes must match `^[a-z0-9][a-z0-9-]{0,39}$` — `shared/types.ts` documents that pattern for
   `Entry.id` and `shared/catalog.ts` enforces the same regex — so a write with an id the Bond could
   never address is a 400 naming `id` instead of a row nobody can reach. Person, session, view and
   role ids stay plain strings: SP01 §2 calls a role id a slug but nothing in `shared/` validates it
   (only `Entry` is), and a uuid person id is SP01 §2's own shape.
4. **A body `id` that is not the path's is a 400** (`invalid body: id must match the path id`), not a
   silent write under the path. SP03 §2 gives `PUT /v1/admin/tools/:id` a body that carries an id too;
   writing one under the other silently is the kind of divergence a later debugging session pays for.
5. **An org tool write is stamped with the host clock** (`auth.now()`), and a body's `updatedAt` is
   dropped by the schema: the live run sent `2000-01-01T00:00:00.000Z` and the answer carried
   `2026-10-16T21:13:58.370Z`. SP03 §2's body is `OrgTool` with no timestamp while SP04 §4 compares
   personal writes by the Bond's `updatedAt` — the asymmetry is H2's decision 10 and this is its route
   side.
6. **`promote` copies the caller's own personal tool, and the copy starts empty.** `roles: []` (the
   admin grants next, SP01 §2's grants are org-only) and fresh view ids, because a personal view is
   its owner's row: `repo.saveOrgTool` would refuse a foreign view id with 403, and the live run shows
   the copy carrying a new id while the original keeps its own. A personal id the admin does not own
   answers **403 `not yours`**, never 404 — the repo only ever reads a personal tool through its owner
   (`host/repo.ts`), so the admin cannot tell a foreign id from an absent one; SP03 §1's "otherwise
   403" covers exactly this. The path `:id` is the org entry's id.
7. **`PATCH /v1/admin/people/:id` is one transaction and an empty body answers the stored person.**
   Name, roles and disabling compose inside `repo.transaction`, so a request that would fail (the
   last admin) leaves none of the three applied; `{}` returns the person untouched, which is SP03 §2's
   "only what the caller sends changes" read literally.
8. **`POST /v1/admin/people` writes the person and their code as one unit of work.** The argon2-free
   hash of the code (`sha256Hex(normalizeCode(code))`) is computed *before* the transaction, because
   `repo.transaction` is synchronous (H2 decision 14); a rollback discards a code nobody received.
9. **`DELETE /v1/admin/sessions/:id` is idempotent per row: 204 when the session exists (live or
   already dead), 404 only when no row holds that id.** SP03 §1's 404 is "id not found"; an already
   revoked session was found. A test pins both.
10. **The route decides no message.** Five routes throw `NotFoundError`/`ForbiddenError` from
    `host/repo.ts` (`unknown person` where the code write would otherwise hit the foreign key, `unknown
    session` for a DELETE that found no row); the app maps the type, exactly as it maps a schema
    failure. The only bodies this file builds are the two 400s of decisions 3 and 4, and neither
    echoes a request value.
11. **`{created}` is the number of org tools the request wrote** — `docs/handovers/c1.md` decision 6's
    reading, which SP03 §2 leaves untyped. If B8a needs ids instead, it is one line here plus one line
    in `shared/host-api.ts`.
12. **The bootstrap window is open while the host holds no org tool at all** (`repo.hasOrgTools`, SP03
    §2). A bootstrap that creates roles but no tool therefore stays repeatable — literal, and worth
    knowing: the live run's second call answered 409 only because the first had written `affine`.
13. **No signing key on the context, and `AppDeps` unchanged.** H6 asked over the cross-slice channel
    and then decided to load the pair itself in `state.ts` (`loadOrCreateSigningKey(config.dataDir)`,
    memoized) — the same shape `createApp` uses for `host-secret` (H4 decision 2). `createApp` stays
    synchronous, which it must: making it `async` would have forced `main.ts`, `health.test.ts` and
    `auth.test.ts` to change, and two of those are not my files. `app.ts` therefore adds mounts only.
14. **No new dependency, no toolchain change, no second boot path.** `crypto.randomUUID`, WebCrypto
    through `shared/encoding.ts`, Elysia's `t.*` and nothing else. `@types/bun` stays what H9 made it:
    a dev-only `devDependency` (recorded in `host/context.md`).
