# H3 — Shared key derivation (`deriveKeys`), same bytes in Bun and txiki.js

Issue that authorizes: **#6** (`[H3] Shared key derivation: authKey / vaultKey / localKey`, Block 1;
`em-curso`). Epic #2 (E01 §7 "One password, two keys"). Contract:
`docs/specs/SP02-auth-and-keys.md` §1; the runtime facts live in `docs/tinyjs.md` §5.

## Files touched

- `shared/auth.ts` — added `deriveKeys(password, salt, iterations) → { authKey, vaultKey, localKey }`,
  the exported `DerivedKeys` interface, the private `KEY_LABELS` (`bond/auth/v1`, `bond/vault/v1`,
  `bond/local/v1`) and the private `hmac` helper. The password is `password.normalize('NFC')` before
  the existing private `derive` turns it into UTF-8 bytes and pays the caller's PBKDF2-HMAC-SHA256
  iteration count; the three keys are HMAC-SHA256 over that `master`. Only `crypto.subtle`
  (`deriveBits`, `importKey`, `sign`) — no new dependency and no `tjs`/`tiny`/DOM, per
  `shared/context.md`. The keys are raw 32-byte `Uint8Array<ArrayBuffer>`: the caller encodes
  (`base64url(authKey)` in the host calls of SP02 §2, `base64url(SHA-256(localKey))` in the
  `PasswordHashV2.check` of SP02 §6). Every existing export (`PBKDF2_ITERATIONS`, `hashPassword`,
  `verifyPassword`, `validateNewPassword`, `generateInviteCode`, `hashInviteCode`, `inviteIsValid`,
  `unlockWait`) kept its signature and behaviour: `hashPassword`/`verifyPassword` still hash the
  password exactly as typed (no NFC step added there, so hashes written by earlier versions keep
  verifying). The module header now names key derivation too.
- `test/auth.test.ts` — exported `KdfVector` and `KDF_VECTORS` (three triples with pinned hex) plus
  six tests: the three vectors derive the pinned bytes; each key is 32 bytes; the three keys differ
  from each other; a different salt changes all three; a different iteration count changes all three;
  an NFD password derives the keys of its NFC form.
- `test/smoke/run.ts` — `KDF_VECTORS` (its own copy, see decision 1), `runtimeBinary()`,
  `kdfDriver()` and `checkKdfVectors()`; `main()` runs the check next to `checkExport()`, prints
  `kdf vectors: ok …` / `FAILED …` and returns 1 when it fails. The header documents it.
- `docs/tinyjs.md` §5 — the execution paragraph with the measured cost and the accepted parameters;
  the old "ainda não foi medido por execução" sentence now points at it.
- `docs/handovers/h3.md` — this file.
- **Not touched:** `test/smoke/smoke.html` and `test/smoke/tools.ts`. The page runs in the webview,
  whose `crypto.subtle` is the system WebKit engine, not txiki.js; the runtime proof belongs in the
  runner (`run.ts`), which is where it is. No page step was added, so `EXPECTED_STEPS` stays 14 and
  the page's own sequence is unchanged.

## What could not be done

- **The smoke did not run in the real checkout.** `bun test/smoke/run.ts` refuses (exit 2) because
  `resources/seed.json` exists, and it is the owner's private seed; the instruction was to report
  instead of forcing. The harness was therefore executed in the copy described in command 6, which
  touches nothing of the owner's. The app under it is the same `tinyjs dev` with the same smoke page
  and the same throwaway app id.
- **Item 3 has a declared limitation.** The vectors ran under `bin/tjs`, the txiki.js 26.6.0 binary
  the launcher uses for the app's backend process, on a bundle of the real `shared/auth.ts`; they did
  not run inside the app's own backend process, because a backend method would be needed for that and
  `backend/main.ts` and `shared/types.ts` are other owners' files. The strict form is one method away —
  exact shape in "What another owner must do" — and then the smoke page could call it instead of the
  harness spawning the runtime.
- **Finding, not part of H3: the current working tree breaks the smoke at step 6.** With the tree as
  it is now, `bun test/smoke/run.ts` in the copy fails step 6 —
  `FAILED 6 tools.open (tool-a, form) (20259 ms) error: timeout (20000 ms); last state: tool-a.login=null`
  — and the audit shows `tool_opened` for `tool-a` with no `login`, `load_failed` or
  `navigation_blocked` event. It reproduced with the harness restored to `HEAD` in the same copy, so
  it is not this slice: the only difference between the failing and the passing runs is the set of
  peer-modified files (`backend/main.ts`, `backend/repo.ts`, `backend/tool-windows.ts`,
  `backend/vault.ts`, `shared/types.ts`, `src/app.ts`, `src/style.css`, `scripts/gen-config.ts`,
  `tinyjs.base.json`), which were reverted to `HEAD` in the passing run. The likely cause is the
  in-flight fill-gate change in `backend/tool-windows.ts` (`hasCredential` → `vaultOrigin`) meeting a
  vault index without the saved origin yet — `[INFERENCE]`, for the coordinator and the owners of
  those files. Unverified in the real checkout (the private seed blocks it).
- `docs/tinyjs.md`'s method note ("Nenhum item foi obtido por execução; tudo é `leitura`", §Método e
  fontes) is now stale — §5 below carries an execution measurement, as §6 already carried an
  execution observation. It is outside §5, the section this story owns, so it was left for the
  coordinator.

## What another owner must do

1. **If the coordinator wants the literal "inside the app's backend process" reading of item 3**, a
   method is needed in two files that are not this slice's: `shared/types.ts` (ApiContract) and
   `backend/main.ts` (handler). Exact shape, following the existing conventions:
   ```ts
   'bond.deriveKeys': [
     { password: string; salt: string; iterations: number },
     { authKey: string; vaultKey: string; localKey: string },
   ];
   ```
   `salt` and the three keys in base64url; the handler awaits
   `deriveKeys(password, base64urlToBytes(salt), iterations)` and encodes the three keys back;
   `meta.window === 'main'` and the session guards exactly as the other methods
   (`docs/arquitetura.md` §2). With that in place, one page step in `test/smoke/smoke.html` calling
   `bond.deriveKeys` per vector and comparing with the config is enough, and `checkKdfVectors()` in
   `run.ts` can be dropped.
2. **`docs/arquitetura.md` §3 (`shared/auth.ts`)** does not list `deriveKeys`/`DerivedKeys` yet; that
   contract file belongs to the coordinator.
3. **H4/B3 will need a base64url encode/decode for the salt and the keys** (SP02 §2 sends
   `base64url(authKey)`, SP02 §6 stores `base64url(sha256(localKey))`). This slice did not add one;
   `shared/auth.ts` only gained the derivation. Whoever adds it owns that decision.
4. **`docs/handovers/h3.md` decides nothing about status.** The issue, the front and the epic keep
   their own state.

## Decisions worth the coordinator's eye

1. **The pinned vectors live twice** (`test/auth.test.ts` and, for the smoke, `test/smoke/run.ts`).
   A `bun:test` module cannot be imported outside the runner — proved by execution: importing
   `test/auth.test.ts` from a plain Bun script throws
   `error: Cannot use describe outside of the test runner.` — and the smoke must compare the Bond
   runtime against the pinned bytes, not against Bun. The two copies cannot drift silently: whichever
   stops matching fails. If the coordinator prefers one home, it is a new file outside this slice's
   list (`test/helpers/kdf-vectors.ts`), imported by both.
2. **The third vector uses the production 600 000 iterations** (~0.4 s in the runtime, ~40 ms in
   Bun), so the pinned set covers the parameters the product actually pays; vectors 1 and 2 stay at
   the cheap 1000 the suite already uses.
3. **`test/smoke/tools.ts` and `test/smoke/smoke.html` are unchanged** on purpose (see "Files
   touched").
4. **The keys are returned as raw bytes, not base64url strings.** SP02 §1 writes "32 bytes, sent as
   base64url": the wire/storage encoding belongs to the caller, and one definition keeps the
   derivation from carrying two formats.
