# S0 — The SP06 seal across txiki.js and Bun: same bytes, cost measured

Issue that authorizes: **#7** (`[S0] Spike: X25519 + HKDF + AES-GCM seal and Ed25519 signatures
across txiki.js and Bun`, Block 1, `em-curso`). Epic #3 (E02, milestones §7 "S0 — spike").
Contract: `docs/specs/SP06-credential-sharing.md` §1 and §3 (key pairs of §2 as far as S0 needs
them); the runtime facts live in `docs/tinyjs.md` §5.

## Files touched

- `shared/seal.ts` — new. The SP06 §3 wire format and the §2 key pairs, with only `crypto.subtle`,
  `TextEncoder` and `btoa`/`atob` (`shared/context.md`). Exports: `SEAL_VERSION`,
  `SEAL_PUBLIC_LENGTH`, `SEAL_NONCE_LENGTH`, `SEAL_SIGNATURE_LENGTH`, the `SealPayload` / `SealKeyPair`
  / `SealOptions` / `OpenOptions` interfaces and the `SealScope` / `SealKind` unions;
  `generateX25519KeyPair`, `generateEd25519KeyPair` (raw 32-byte public key + 48-byte PKCS#8 private
  key, RFC 8410); `importX25519PublicKey`, `importX25519PrivateKey`, `importEd25519PublicKey`,
  `importEd25519PrivateKey`; `sign` / `verify` (Ed25519, over the body when called from `seal`);
  `seal(payload, recipientX25519Public, senderEd25519Private, options?)` →
  `base64url(body || sig)` and `open(sealed, options)` → `SealPayload | null`. Private helpers:
  base64url encode/decode, `concatBytes`, `hmacSha256`, `hkdfSha256` (RFC 5869 over HMAC, per SP06
  §1), `sharedSecret` (X25519 `deriveBits`), `isSealPayload`. No import from any other module; no new
  dependency; no secret reaches a log, an error or a string the caller did not ask for.
- `test/seal.test.ts` — new. The pinned vectors (own copy) and 19 tests: the pinned `sealed` strings
  are reproduced byte for byte; the body layout is `0x01 || eph.public || nonce || ct || sig`; the
  sealed bytes carry neither username nor secret in clear; two seals of one payload differ; the pinned
  vectors open to the pinned payloads; a share to a fresh pair opens with it; a flipped bit in the
  body, in the signature, in the AAD (another `credentialId`, another `to`), another recipient pair,
  another sender key and a payload addressed to somebody else are all refused; malformed base64url,
  truncated input and padding are refused without throwing; the pinned Ed25519 signature is
  deterministic and verifies; a flipped signature, a flipped message, another key and a truncated
  signature do not verify; both key pairs export the SP06 §2 shapes.
- `test/smoke/run.ts` — added the SP06 §3 section beside the SP02 §1 one: the pinned data
  (`SEAL_KEYS`, `SEAL_VECTORS`, `SEAL_TAMPERED`, `SEAL_SIGNATURE_VECTOR`, `SEAL_REFUSALS`), the
  `SealedVectors` interface, `sealDriver()` and `checkSealVectors()`, both following `kdfDriver()` /
  `checkKdfVectors()` step by step; `main()` runs the check after `checkKdfVectors()`, prints
  `seal vectors: ok …` / `FAILED …` and returns 1 when it fails. The header sentence about the
  harness's runtime checks now names both. Nothing else was touched: no page step, so `EXPECTED_STEPS`
  stays 14 and `test/smoke/smoke.html` / `test/smoke/tools.ts` are untouched.
- `docs/tinyjs.md` §5 — the "Primitivas de criptografia nativas" bullet now says which primitives were
  measured by execution, its "Beyond PBKDF2" bullet points at the new paragraph, and the new
  **Observed by execution (2026-10-16): X25519, Ed25519, AES-256-GCM and the SP06 §3 seal in the Bond
  runtime** paragraph carries the method, the cost per operation in both runtimes, the native-HKDF
  finding and the accepted parameters.
- `docs/handovers/s0.md` — this file.

## What could not be done

- **The seal check did not run inside a full smoke**, only through the real `checkSealVectors()` of
  `test/smoke/run.ts`. The harness needs the private seed and the whole page-driven scenario for that,
  which the brief excluded. Two consequences, both declared: the smoke's own line
  `seal vectors: ok …` is not observed yet (whoever runs the full smoke sees it next to
  `kdf vectors: ok …`), and the temporary `test/smoke/run-importable.ts` copy is an artefact of this
  run — it was deleted by the harness, and the generated `test/smoke/.gerado/seal/` output is the
  gitignored directory the smoke already uses.
- **The vectors did not run inside the app's own backend process.** They ran under `bin/tjs`, the
  txiki.js 26.6.0 binary the tinyjs launcher execs for that process, on a bundle of the real
  `shared/seal.ts`. The literal reading needs a backend method, and `backend/main.ts` and
  `shared/types.ts` belong to other owners — the exact shape is in "What another owner must do".
- **The cross-runtime round trip is proven through pinned bytes, not through a live hand-off.** No
  single process can run Bun's `subtle` and txiki.js's at once, so the bridge is the pinned `sealed`
  string: Bun produces it, txiki.js must produce the identical bytes and open that string, and Bun
  opens it in the unit test. A `[INFERENCE]` is not involved: both runtimes' outputs are compared to
  the same constants, and either one drifting fails its check.
- **`docs/tinyjs.md`'s "Method and sources" line** ("Nenhum item foi obtido por execução; tudo é
  `leitura`") is stale, exactly as H3 reported: §5 and §6 now carry execution evidence. It sits
  outside §5, the section this story owns, so it was left for the coordinator.

## Decisions worth the coordinator's eye

1. **The pinned vectors live twice** (`test/seal.test.ts` and, for the runtime check,
   `test/smoke/run.ts`), the same call H3 made and for the same reason: a `bun:test` module cannot be
   imported outside the runner (H3 proved it by execution), and the smoke must compare the Bond
   runtime against pinned bytes, not against Bun. This copy drops `signatureHex`, which only the unit
   test asserts (the smoke's whole-string comparison and `open` already cover the signature). If one
   home is preferred, it is a new file outside this slice's list (`test/seal-vectors.ts`), imported by
   both.
2. **`open` returns `SealPayload | null`, never an error.** SP06 §3 ends every failure in one reason
   (`invalid share`), so the module gives one outcome and the caller maps it to that reason; SP06 §3
   steps 4 and 5 (metadata, tool visibility, origin) stay with the caller, which has the host's data.
3. **`open` takes the recipient's own public key** besides its private key. The HKDF salt is
   `eph.public || recipient.x25519Public` (SP06 §3) and WebCrypto cannot derive a public key from a
   PKCS#8 private key, so the opener passes the pair it stored and sent to `PUT /v1/keys`. Worth a
   line in SP06 §3's "Opening", which lists only the private half implicitly.
4. **Key pairs cross the API as bytes, not as `CryptoKey`**: raw 32-byte public key and PKCS#8 private
   key, exactly what SP06 §2 stores (the same choice H3 made for the three derived keys). The
   `import*` functions exist for callers that want the imported handles.
5. **`seal` accepts a pinned ephemeral pair and nonce** (`SealOptions`). That seam is what makes the
   vectors reproducible byte for byte, and it is documented as vector-only; K stories call `seal`
   without it, so every real share gets a fresh ephemeral key and a fresh nonce.
6. **The payload's key order is fixed by `seal`**, not by the caller's object: the plaintext is built
   field by field in SP06 §3's order, because a pinned vector hinges on those bytes.
7. **HKDF stays hand-rolled over HMAC** as SP06 §1 asks, even though the measurement shows `subtle`
   resolves `HKDF` natively in both runtimes (~0.01 ms per call): following the spec keeps the seal
   from depending on that support, and the measured cost of the JS path is inside the `seal`/`open`
   figures recorded in `docs/tinyjs.md` §5. If the coordinator prefers the native primitive, that is
   a spec change for §1, with the same bytes and a smaller cost.
8. **`docs/handovers/s0.md` decides nothing about status.** The issue, the front and the epic keep
   their own state.
